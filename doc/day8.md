# Day 8 レポート — ログインが必要な管理画面を公開したい

## 1. 目的

### 1.1 背景（どの時代の困りごとか）

- **時代⑤（ゼロトラスト）**：「社内のネットワークの中だから安全」ではなく、リクエストごとに「誰が、何をしようとしているか」を確かめる。そのための関所として、アプリの手前に認証を置く（Google の BeyondCorp のアクセスプロキシ）

### 1.2 確かめたいこと

1. nginx の Basic 認証は、どこまで使えるか
2. 認証を専用のサービスに任せ（`auth_request`）、結果をアプリに渡すとどうなるか
3. 入口を迂回されたとき、認証結果の偽装を防げるか
4. 認証が正しくても、他人のデータが見えてしまうことはあるか

事前チェックで整理した2つのルール：

- **ルールA**：`/admin/users` は役割が admin の人だけ（URL と役割だけで判断できる → 入口でできる）
- **ルールB**：`/mypage/orders/:id` はその注文の持ち主だけ（注文のデータが必要 → アプリにしかできない）

---

## 2. 手法

### 2.1 構成（`compose.day8.yml`）

```
client ──→ nginx(8701, 8702) ──→ api-a(アプリ: 注文の画面)
                 │ auth_request
                 └──────────────→ auth(認証サービス。同じ jar を別名で起動)
   └─────────── 直接 ──────────→ api-a(Step 3: nginx を通らない経路)
```

- ユーザー：yamada（staff）、sato（staff）、boss（admin）
- 注文：1 と 3 は yamada、2 は sato のもの

### 2.2 トークン（`auth.clj`）

```
yamada . staff . 1795610290 . 6861a569…0417
ユーザー  役割    有効期限(UNIX秒)  署名 = HMAC-SHA256(秘密の鍵, 前の3つ)
```

認証サービスがログイン時に発行し、Cookie で渡す。秘密の鍵を持たない人には、正しい署名が作れない。

### 2.3 アプリの切り替え

| 環境変数 | 値 | 意味 |
|---|---|---|
| `TRUST_AUTH` | `header` | nginx が付けた `X-Auth-User` をそのまま信じる |
| | `signed` | トークンの署名を、アプリ自身でも検証する |
| `AUTHZ` | `none` | ログインしていれば、どの注文でも見せる |
| | `owner` | 注文の持ち主にだけ見せる |

`/admin/users`（`admin-users`）は、役割の確認を入口に任せており、アプリでは何も確かめない作りにした。

### 2.4 nginx の入口（`nginx/day8.conf`）

| ポート | 中身 |
|---|---|
| 8701 | `/mypage/` に Basic 認証（`auth_basic`）。認証したユーザー名を `X-Auth-User` で渡す |
| 8702 | `/login` は認証サービスへ。`/mypage/` は `auth_request /_auth`、`/admin/` は `auth_request /_auth_admin`（`require=admin`）。認証サービスの返事の `X-Auth-User` を取り出し、上書きしてアプリに渡す |

### 2.5 仕組みの分担

| やっていること | 担当 |
|---|---|
| ユーザー名とパスワードを確かめる（Basic 認証） | nginx |
| ログインしたら、署名付きトークンを渡す | 認証サービス |
| アプリに送る前に、トークンが本物かを問い合わせる | nginx（`auth_request`） |
| 役割が admin かを確かめる（ルールA） | 認証サービス＋nginx |
| 誰からのリクエストかを判断する | アプリ（`current-user`） |
| 注文の持ち主にだけ見せる（ルールB） | アプリ（`my-order`） |

## 3. 結果

### 3.1 Step 1：Basic 認証（8701）

| 測定 | 結果 |
|---|---|
| パスワードなし | 401（nginx が返した） |
| `yamada:pass-y` | 200、`you: yamada`、注文1 |
| curl が送った認証の行 | `Authorization: Basic eWFtYWRhOnBhc3MteQ==`（Base64 を戻すと `yamada:pass-y`） |

### 3.2 Step 2：認証の前段化（8702）

| 測定 | 結果 |
|---|---|
| ログイン前に `/mypage/orders/1` | 401 |
| yamada でログイン | `{"login":"yamada","role":"staff"}`、トークン `yamada.staff.1795610290.6861a5…` |
| ログイン後に `/mypage/orders/1` | 200、`you: yamada` |
| yamada のまま `X-Auth-User: sato` を付ける | `you: yamada`（上書きされた） |
| yamada で `/admin/users` | 403 |
| boss で `/admin/users` | 200、ユーザー一覧 |

### 3.3 Step 3：nginx を迂回したなりすまし（`api-a:3000` に直接）

| 送ったもの | `TRUST_AUTH=header` | `TRUST_AUTH=signed` |
|---|---|---|
| `X-Auth-User: sato` で `/mypage/orders/2` | **200、sato の注文2** | 401（not logged in） |
| `X-Auth-User: boss` で `/admin/users` | **200、ユーザー一覧** | **200、ユーザー一覧** |
| 偽の署名のトークン（sato）で `/mypage/orders/2` | — | 401（not logged in） |

### 3.4 Step 4：IDOR（yamada が nginx 経由・本物のトークンで）

| 測定 | `AUTHZ=none` | `AUTHZ=owner` |
|---|---|---|
| `/mypage/orders/1`（自分の注文） | 200 | 200 |
| `/mypage/orders/2`（sato の注文） | **200、sato の注文** | 403（not your order） |

## 4. 考察

### 4.1 Basic 認証は手軽だが、規模が大きくなると扱えない

nginx の設定2行とファイル1つで、アプリを変えずに守れた。一方、送られる `Authorization` は暗号ではなく Base64 で、誰でも `yamada:pass-y` に戻せる。パスワードが毎回のリクエストに付いて送られるので、https が必須である。ログアウトがなく、ユーザーの追加にはファイルの書き換えが要り、役割の区別もできない。

### 4.2 認証の前段化で、入口がログインと役割を確かめる

`auth_request` では、nginx がアプリに送る前に認証サービスに問い合わせ、だめならアプリに届けずに断った（401、403）。認証サービスの返事から取り出した `X-Auth-User` で上書きして送るので、nginx を通る限り、クライアントが書いた値はアプリに届かない。

`/mypage/` と `/admin/` は問い合わせ先が違うだけで、後者では役割まで確かめる。これがルールA（URL と役割だけで決まる認可）を入口で行う形である。トークンは署名付きなので、認証サービスはデータベースを引かずに、鍵で計算し直すだけで本物かを確かめられる。

### 4.3 入口だけに頼ると、迂回されたときに全部が破られる

nginx を通らずにアプリへ直接送ると、ヘッダーを1行書くだけで、ログインせずに sato の注文も admin の画面も見えた。アプリは「`X-Auth-User` は nginx が付けたもの」と信じているが、迂回した経路ではそれを書いたのは攻撃者である（Day 7 の `X-Forwarded-For` と同じ構図）。

アプリでトークンの署名を検証すると（`signed`）、ヘッダーの偽装も偽の署名も弾かれた。ところが、`/admin/users` だけは通り続けた。`signed` で変わったのは `current-user` だけで、`admin-users` は「入口で確かめているから」と何も確かめていなかったためである。アプリでも `verify-token` を呼び、役割を確かめる必要がある。

この二重チェックは無駄な重複ではない。入口は「明らかにだめなものを早く断る」、アプリは「最後に通してよいかを自分で決める」と役割が違う。署名付きトークンなら、アプリでの検証はデータベースにも認証サービスにも問い合わせないので、コストはごくわずかである。経路を塞ぐこと（ネットワークを分ける、NetworkPolicy）と、署名の検証は、両方行う。

### 4.4 認証が正しくても、データごとの認可がなければ他人のデータが見える

yamada は、nginx 経由で本物のトークンを使い、アプリも署名を検証していたのに、URL の番号を変えるだけで sato の注文を見られた（IDOR）。認証（あなたは yamada）は正しいが、認可（yamada が注文2を見てよいか）をしていなかった。注文の持ち主は注文のデータを読んで初めて分かるので、この判断はアプリにしかできない（ルールB）。`AUTHZ=owner` で持ち主を確かめると、403 で断られた。

### 4.5 重ねた守りの全体像

| 守り | 担当 | 防いだもの |
|---|---|---|
| ログインしていない人を断る | nginx＋認証サービス | 誰だか分からないアクセス |
| `X-Auth-User` を上書きする | nginx | nginx 経由での偽装 |
| 役割を確かめる（ルールA） | nginx＋認証サービス | staff の管理画面へのアクセス |
| トークンの署名をアプリでも検証する | アプリ | nginx を迂回した偽装 |
| 注文の持ち主を確かめる（ルールB） | アプリ | 他人のデータの閲覧（IDOR） |

どれか1つが欠けると、その行の「防いだもの」が通ってしまう。入口は関所であって、城の中の各部屋の鍵ではない。

---

## 5. 結論

1. Basic 認証は手軽だが、パスワードが毎回ほぼそのまま送られ、ユーザーや役割が増えると扱いきれない
2. `auth_request` で認証を専用のサービスに任せると、入口でログインと役割（ルールA）を確かめ、だめなものをアプリに届く前に断れる。認証結果は nginx が上書きして渡すので、nginx 経由では偽装できない
3. 入口を迂回されると、ヘッダーを信じるアプリは簡単になりすまされる。アプリでも署名付きトークンを検証し、すべての画面で確かめる。経路を塞ぐことと重ねて使う
4. 認証が正しくても、データごとの認可（ルールB）がなければ、URL の番号を変えるだけで他人のデータが見える。これはデータを持つアプリにしかできない

### 残った課題

- `admin-users` でも `verify-token` を呼び、役割を確かめるようにする（Step 3 で迂回されたまま）
- Compose のネットワークを分けて、client から api-a に直接届かないようにする（経路を塞ぐ守り）
- 事後チェックは未実施（例：認証サービスが落ちたら `auth_request` はどう振る舞うか、トークンの有効期限を長くしたら何が起きるか）
