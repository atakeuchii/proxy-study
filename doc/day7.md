# Day 7 レポート — 悪意のあるアクセスや攻撃から守りたい

## 1. 目的

### 1.1 背景（どの時代の困りごとか）

- **時代③（C10K と遅いクライアント）**：わざとゆっくり送る相手で、サーバの資源を占有させる攻撃（slowloris など）は、遅いクライアントの問題を悪用したものである
- **時代⑤（ゼロトラスト）**：「社内の IP なら信頼する」という境界型の考え方は、IP の判断を誤ると簡単に破られる。入口のプロキシは、何を信頼し、何を捨てるかを決める関所になる

### 1.2 確かめたいこと

1. `X-Forwarded-For` の偽装で IP 制限を突破できるか。realip でどう防ぐか
2. レート制限は、速さを超えたリクエストをどう扱うか
3. 遅い攻撃は、どこで資源を占有するか。nginx とタイムアウトでどう防ぐか
4. エラーページやヘッダーから、何が漏れているか

**注意**：攻撃の再現は、すべて自分のローカルの Docker 環境の中だけで行った。

## 2. 手法

### 2.1 構成（`compose.day7.yml`）

```
client ──→ proxy(nginx: 8601〜8607) ──→ api-a(枠 16本)
  └──────────── 直接 ──────────────────→ api-a:3000(Step 3 の比較用)
```

### 2.2 アプリ（`server.clj` の `admin`）

- `GET /admin`：クライアントの IP が `10.` で始まる（社内とみなす）ときだけ 200、それ以外は 403
- IP をどこから取るかを `ADMIN_IP_SOURCE` で切り替える
  - `xff-left`：`X-Forwarded-For` の左端（よくある間違い）
  - `x-real-ip`：nginx が付ける `X-Real-IP`（nginx が求めた値を信じる）

### 2.3 nginx の入口（`nginx/day7.conf`）

| ポート | 中身 | Step |
|---|---|---|
| 8601 → 8611 | 手前のプロキシ（CDN や ALB の代わり）→ realip なし | 1 |
| 8602 → 8612 | 手前のプロキシ → realip あり（`set_real_ip_from 127.0.0.1`、`real_ip_header X-Forwarded-For`、`real_ip_recursive on`） | 1 |
| 8603 / 8604 | 1 IP あたり毎秒5件。burst=10 nodelay ／ burst なし | 2 |
| 8605 | 遅い攻撃：タイムアウトは既定（ヘッダー60秒、本文60秒） | 3 |
| 8606 | `client_header_timeout 10s` ＋ `limit_conn` 1 IP あたり10本 | 3 |
| 8607 | `server_tokens off` ＋ セキュリティヘッダー | 4 |

### 2.4 仕組みの分担

| やっていること | 担当 |
|---|---|
| 社内の IP からだけ管理画面を見せる | アプリ |
| 信頼できる相手から来たときだけ、ヘッダーの本当の IP を採用する | nginx（realip） |
| 1 IP あたりの速さ・同時接続数を制限する | nginx（`limit_req`、`limit_conn`） |
| ヘッダーをいつまでも待たない | nginx（`client_header_timeout`） |
| バージョンを出さない、ブラウザに安全のための指示を出す | nginx（`server_tokens`、`add_header`） |

### 2.5 遅い攻撃（`scripts/slow-attack.sh`）

| 種類 | やること |
|---|---|
| `header`（slowloris） | ヘッダーを5秒ごとに1行ずつ送り、ヘッダーの終わりを送らない |
| `body` | ヘッダーは送り切り、本文（100KB と宣言）を5秒ごとに10バイトずつ送る |

サーバに切られたことには、次に書き込んだとき（最大5秒遅れ）に気づく。

## 4. 考察

### 4.1 IP の判断は、どのプロキシを信頼するかを知っている入口に任せる

`X-Forwarded-For` は、プロキシを通るたびに右に追記される。左端はクライアントが自由に書けるので、アプリが左端を信じると、1行書き足すだけで社内の IP を名乗れた。

```
X-Forwarded-For: 10.0.0.5,      172.18.0.4,          127.0.0.1
                 攻撃者が書いた   手前のプロキシが追記   内側の nginx が追記
```

realip のない 8601 では、内側の nginx が直接の接続元（手前のプロキシ）を `X-Real-IP` に入れたため、偽装は防げたものの、**全員が 127.0.0.1 に見えた**。ログもレート制限もユーザーを区別できず、許可リストに手前のプロキシの IP が入っていれば全員が通ってしまう。

realip のある 8612 では、nginx が右から辿り、信頼できるプロキシ（127.0.0.1）を飛ばして、最初の信頼できない IP（172.18.0.4）を採用した。攻撃者が書いた左側までは辿り着かない。アプリは自分で解釈するのをやめ、nginx の結論（`X-Real-IP`）を使う。

自宅サーバ（Cloudflare）なら、`set_real_ip_from` に Cloudflare の IP 範囲（Tunnel なら `cloudflared`）、`real_ip_header` に `CF-Connecting-IP` を書く。

### 4.2 レート制限は「瞬間のまとまり」を許し、「続くこと」を止める

毎秒5件は「200ms に1件」であり、一度に来た30件のうち、burst なしでは1件だけが通った。burst=10 では、それに加えてバケツに入る10件が受け付けられ、`nodelay` によって待たされずに処理された。ブラウザはページを開くだけで一瞬に何件ものリクエストを出すので、burst なしでは正規のユーザーも断られる。

レート制限のキーは接続元の IP なので、Step 1 の realip が正しく設定されていることが前提になる。

### 4.3 遅い攻撃が資源を占有するのは「待ち方」による

事前チェックでは「Jetty に直接 slowloris を向けると、16本の枠が埋まって止まる」と考えたが、実際には**ヘッダーを遅く送る攻撃では、Jetty の枠は1本も使われなかった**。一方、本文を遅く送る攻撃では、20本で16本の枠がすべて埋まり、普通のリクエストが止まった。

```
ヘッダーを受け取る  Jetty の見張り役(イベント駆動)が、届いた分だけ読む → 枠は使わない
     ↓ ヘッダーが完了
本文を受け取る      枠のスレッドに渡し、ハンドラ(upload)が .read で本文を読む
                   → 届くまでスレッドが止まって待つ
```

Jetty も nginx と同じく、ヘッダーの段階はイベント駆動で受けるので、ヘッダーが永遠に完了しない接続は枠に渡らない。slowloris は、Apache の prefork のように「接続を受けた瞬間に1本の枠が担当する」サーバを狙った攻撃である。しかし、Ring のハンドラの中で本文を読むと、その間スレッドが拘束されるので、本文を遅く送る攻撃は効く。Day 5 の事後チェック（`proxy_request_buffering off`）と同じ構図である。

nginx を挟むと、本文を全部受け取るまでアプリに渡さないので、本文を遅く送る攻撃が20本あっても、Jetty の枠は使われなかった。

### 4.4 タイムアウトと接続数の上限は、nginx 自身を守る

nginx はアプリを守るが、遅い接続を代わりに抱えているのは nginx 自身である。8606 では、2つの対策が別々の攻撃に効いた。

| | ヘッダーを遅く送る | 本文を遅く送る |
|---|---|---|
| `client_header_timeout 10s` | 効いた（20本とも10秒で切られた） | 効かない（ヘッダーはすぐ完了している） |
| `limit_conn perconn 10` | 効かない（数えるのはヘッダーを受け取り終えた後） | 効いた（11本目以降を断った） |
| nginx を挟むこと自体 | アプリに届かない | アプリに届かない |

`client_header_timeout` はヘッダー全体を受け取る時間の上限なので、少しずつ送り続けても逃れられない。一方、本文のタイムアウトは「前に受け取ってから次まで」の間隔なので、上限の範囲内で少しずつ送り続ける攻撃は止めきれない。どれか1つで全部を防げるわけではなく、重ねて使う。

### 4.5 情報を漏らさない

既定では、`Server` ヘッダーとエラーページの2か所に、nginx の正確なバージョンが出ていた。隠しても脆弱性はなくならないが、攻撃者の下調べを楽にさせない。本当の対策は最新に保つことである。

セキュリティヘッダーは、ブラウザへの指示である。nginx でまとめて付ければ、裏のアプリがいくつあっても同じ守りがかかる。ただし `Strict-Transport-Security` は https で返したときだけブラウザに有効なので、TLS を終端する入口に付ける。

### 4.6 事後チェックで分かったこと

- **`set_real_ip_from` を広くしすぎると**（`0.0.0.0/0`）：すべての IP が信頼できるプロキシになり、右から全部を飛ばして左端の `10.0.0.5` を採用する。左端を信じるのと変わらない。自分が管理するプロキシの IP だけを、できるだけ狭く書く（Cloudflare なら公開されている範囲、AWS なら ALB のサブネットだけ）
- **NAT の後ろのユーザーと、IP ごとのレート制限**：大学の200人が同じ IP に見えると、全員で毎秒5件を取り合い、正規のユーザーがまとめて締め出される。キーをセッションの Cookie や API キーにできるが、nginx はそれが本物かを確かめないので、値を変えればすり抜けられる。IP ごとの制限はゆるく残し、ユーザーごとの制限は本物だと確かめた値で数える（Day 8 の認証の前段化につながる）

## 5. 結論

1. `X-Forwarded-For` の左端を信じると、1行の偽装で IP 制限を突破される。どのプロキシを信頼するかを知っている入口の nginx が realip で本当の IP を求め、アプリはその結論を使う。信頼する範囲は、自分のプロキシだけに狭く絞る
2. レート制限は burst で瞬間のまとまりを許し、超える状態が続くことだけを止める。キーが IP なら realip が前提で、NAT の後ろのユーザーには別の数え方が要る
3. 遅い攻撃が資源を占有するかは、サーバの待ち方による。Jetty はヘッダーの段階では枠を使わないが、ハンドラで本文を読むと枠が埋まる。nginx を挟めばアプリは守られ、タイムアウトと接続数の上限が nginx 自身を守る
4. nginx でバージョンを隠し、セキュリティヘッダーをまとめて付けると、裏のすべてのアプリに同じ守りがかかる
