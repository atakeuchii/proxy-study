# Day 3 レポート — 裏のサーバが1台落ちた・遅くなった

## 1. 目的

### 1.1 背景（どの時代の困りごとか）

- **時代①（障害に反応する）**：手前にプロキシを置くと、落ちたサーバを避けて配れる。では、プロキシはいつ「失敗した」と判断し、何をするのか
- **時代④（サービス間の通信が壊れやすい）**：リトライは失敗を隠してくれるが、二重処理や負荷の増幅という副作用がある

### 1.2 確かめたいこと

1. サーバが**落ちた**とき、nginx は何をするか。ユーザーにエラーは見えるか
2. サーバが**遅くなった**とき、nginx は何をするか
3. POST をやり直すと何が起きるか。冪等キーで防げるか
4. 各段でリトライすると、回数はどう増えるか

---

## 2. 手法

### 2.1 構成（`compose.day3.yml`）

```
client ──→ proxy(nginx: 8101〜8106) ──→ api-a / api-b / api-c ──→ redis(注文と冪等キー)
                                         └ 管理用ポート 9100: /fault(障害注入)
```

### 2.2 障害注入（管理用ポートの `/fault`）

| 指定 | 効き方 |
|---|---|
| `down=true` | 本体の待ち受けを閉じる。接続は即座に拒否される（connection refused） |
| `delay-ms=3000` | 処理を**終えた後**、返事を返す前に3秒待つ |
| `error-rate=1.0` | 処理せずに 500 を返す |

### 2.3 nginx の設定（`nginx/day3.conf`）

| ポート | 設定 |
|---|---|
| 8101 | 既定のまま（接続の失敗とタイムアウトならやり直す。POST は送った後ならやり直さない。`max_fails=1 fail_timeout=10s`。`proxy_read_timeout 60s`） |
| 8102 | 8101 と同じサーバの組で、やり直しなし（`proxy_next_upstream off`） |
| 8103 | `proxy_read_timeout 1s`。POST は送った後ならやり直さない |
| 8104 | 8103 に加えて、POST もやり直す（`non_idempotent`） |
| 8105 | 2段構え。外側も内側も、500 なら別のサーバでやり直す（各段最大3台） |
| 8106 | 1段だけ。500 なら別のサーバでやり直す（最大3台） |

### 2.4 手順

| Step | 障害 | 内容 |
|---|---|---|
| 1 | api-c を `down` | 8102 と 8101 に GET を9回ずつ。8101 に POST を4回 |
| 2 | api-c に `delay-ms=3000` | 8101 と 8103 に GET を3回ずつ |
| 3 | 同上 | 8103 と 8104 に POST を3回ずつ。8104 に冪等キー付きの POST を3回 |
| 4 | 3台とも `error-rate=1.0` | 8106 と 8105 に GET を1回ずつ |

---

## 3. 結果

### 3.1 Step 1：落ちたサーバ

| 測定 | 結果 |
|---|---|
| 8102（やり直しなし）GET 9回 | 3回目だけ 502、残り8回は 200 |
| 8101（やり直しあり）GET 9回 | 9回とも 200。api-c に当たった1件のログ：`connect() failed (111: Connection refused)`、`upstream server temporarily disabled`、`up=c, b ust=502, 200` |
| 8101 POST 4回 | 4回とも 201。注文の合計は4件 |

### 3.2 Step 2：遅くなったサーバ

| 測定 | api-c に当たった1件 |
|---|---|
| 8101（タイムアウト60秒） | 200、2.90秒。`ust=200 urt=3.006` |
| 8103（タイムアウト1秒） | 200、0.97秒。`upstream timed out`、`up=c, b ust=504, 200 urt=1.003, 0.003` |

### 3.3 Step 3：注文

| 測定 | ユーザーに返ったもの | 作られた注文 |
|---|---|---|
| 3-1 8103（POST をやり直さない） | 3件目が 504（1.00秒） | 3件（`1番@b, 2番@a, 3番@c`） |
| 3-2 8104（POST もやり直す） | 3件とも 201 | **4件**（`1番@c, 2番@b, 3番@a, 4番@b`）。1件目のログ：`up=c, b ust=504, 201` |
| 3-3 8104＋冪等キー | 1件目 201、2件目 `replayed: true, answered-by: b`、3件目 201 | 3件（`1番@a, 2番@c, 3番@a`）。2件目のログ：`up=c, b ust=504, 200` |

### 3.4 Step 4：リトライストーム

| 測定 | ユーザーに返ったもの | 裏のやりとり |
|---|---|---|
| 8106（1段） | 500 | api に3回（`ust=500, 500, 500`） |
| 8105（2段） | 500 | 外側が内側の 9201〜9203 に3回、内側がそれぞれ api に3回。同じ `rid` で4行のログ、api には合計9回 |

## 4. 考察

### 4.1 「落ちた」は速く分かり、安全にやり直せる

api-c が落ちていると、接続を張る段階で即座に拒否された。nginx はリクエストを1バイトも送っていないので、別のサーバでやり直しても、処理が二重になることはない。そのため既定の 8101 では、GET も POST もやり直され、ユーザーにはエラーが一度も見えず、注文も4件のままだった。

やり直しを切った 8102 でも、エラーは1回だけだった。パッシブヘルスチェック（`max_fails=1 fail_timeout=10s`）が、1回失敗した api-c を10秒間使わないと決めたためである。逆に言えば、nginx（OSS 版）は実際のリクエストが1回失敗するまで、api-c が落ちていることに気づけない。

### 4.2 「遅い」はタイムアウトで初めて失敗になる

api-c が遅いだけのとき、既定の 8101 は返事を3秒待ち、ユーザーも3秒待たされた。返事自体は正常なので、nginx はこれを失敗とは扱わない。`proxy_read_timeout` を1秒にした 8103 では、1秒で見切って別のサーバでやり直し、ユーザーの待ち時間は約1秒になった。

ただし、このとき api-c は処理を終えていた（`delay-ms` は処理の後に待つ設定）。この GET は api-c と api-b の2か所で処理されている。GET のように何度処理しても結果が変わらないリクエストなら問題ないが、そうでなければ二重処理になる。

### 4.3 タイムアウトの後は「成功したかどうか分からない」

| | ユーザーに見えるもの | 実際 |
|---|---|---|
| 3-1 やり直さない | 504 のエラー | 注文はできている |
| 3-2 無理にやり直す | 全部成功 | 黙って二重になる |

3-1 では、nginx は既定どおり POST をやり直さず 504 を返したが、注文（3番@c）は作られていた。ユーザーは失敗したと思ってやり直すので、結局二重になる。やり直す役が nginx からユーザーに移っただけで、問題は消えていない。

3-2 では、ユーザーには全部成功に見えるのに、3件の操作で4件の注文ができた。エラーすら見えないので、3-1 より気づきにくい。

プロキシからは「タイムアウトした」ことしか分からず、「相手が処理を終えていたか」は分からない。この不確かさは、プロキシの設定だけでは解消できない。

### 4.4 冪等キーで、アプリが同じ操作を見分ける

3-3 では、nginx のやり直しは 3-2 と同じだったのに、注文は3件のままだった。api-c がキー `order-2` で注文を作って結果を Redis に保存し、やり直しを受けた api-b がその結果を見つけて、注文を作らずに返した（`replayed: true`）。ユーザー自身が同じキーで送り直した場合も、同じように防げる。

冪等キーの記録は、全サーバから見える場所（Redis）に置く必要がある。リトライは別のサーバに届くからで、Day 2 でセッションを外出ししたのと同じ理由である。また、「キーがまだ無いときだけ登録する」を Redis の1回の操作（`SET ... NX`）で行っている。確認と登録を別々にすると、2台がほぼ同時に「まだ無い」と判断し、両方が注文を作ってしまう。

### 4.5 リトライは段数の掛け算で増える

3台とも壊れているとき、ユーザーの1回のリクエストは、1段なら3回、2段なら 3 × 3 = 9回になった。壊れたサーバを助けようとしたリトライが、そのサーバへの負荷を9倍にしている。各段のログが同じリクエスト ID を持っていたので、1回のリクエストが何回に増えたかを追跡できた。

対策は、リトライを1か所（例えば一番外側）だけで行うこと、リトライの回数に上限を設けること、失敗が続いたら呼ぶのをやめること（サーキットブレーカー）である。

---

## 5. 結論

1. 接続の段階での失敗（connection refused）は、リクエストがアプリに届いていないので、POST でも安全にやり直せる。nginx は既定でそうしており、ユーザーにはエラーが見えなかった
2. 遅いサーバは、タイムアウトを短くして初めて「失敗」として避けられる。ただし、タイムアウトしたリクエストは相手が処理済みかもしれず、やり直すと二重に処理される
3. タイムアウトした POST は、やり直さなければユーザーが再送して二重になり、やり直せば黙って二重になる。プロキシでは解決できず、アプリが冪等キーで同じ操作を見分ける必要がある。冪等キーの記録は、全サーバから見える場所に置く
4. 各段でリトライすると、回数は段数の掛け算で増える（1段で3回、2段で9回）。リトライは1か所に絞る

### 残った課題

- `docker compose stop` でコンテナごと止めた場合（connection refused ではなく、接続先が存在しない場合）の挙動は未確認
