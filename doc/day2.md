# Day 2 レポート — アクセスが増えて、1台では捌けなくなった

## 1. 目的

### 1.1 背景（どの時代の困りごとか）

- **時代③（C10K 問題と遅いクライアント）**：1リクエスト1スレッドのサーバでは、遅いクライアントの相手をしている間、スレッド（枠）が拘束される。CPU は空いているのに、枠が足りなくなる
- **時代①（台数を増やす）**：台数を増やすと「どのサーバに配るか」が問題になる。配り方によって負荷が偏り、またサーバの中に状態（セッション）があると、別のサーバに届いたときに失われる

### 1.2 場面

アプリへのアクセスが増え、応答が遅くなった。CPU には余裕があるのに、新しいリクエストが待たされる。台数を増やしたら、今度はログイン状態が勝手に消えるようになった。

### 1.3 確かめたいこと

1. 「捌ける数 ＝ 枠の数 ÷ 1リクエストが枠を占有する時間」が、実測で成り立つか
2. 遅いクライアントは、どのようにして枠を占有するのか
3. nginx のバッファリングは、それをどれだけ解消するのか
4. 配る回数が均等でも負荷が偏るのはなぜか。ラウンドロビンと `least_conn` で何が違うか
5. 台数を増やすとセッションが消えるのはなぜか。`ip_hash` と、セッションの外出しで何が違うか

## 2. 手法

### 2.1 環境

- 実行環境：Windows の WSL（Ubuntu）上の Docker
- 構成（`compose.day2.yml`）

```
client(負荷をかける側) ──→ proxy(nginx: 8001〜8005) ──→ api-a / api-b / api-c
       └────────────── 直接 ──────────────────────────→ api-a:3000 (Step 1)
                                                         redis (Step 4)
```

- 負荷は、ホストからではなく client コンテナの中から、Compose の内部ネットワーク越しにかけた（ホストから叩くと Docker のポート公開の中継が挟まり、その中継もデータを溜め込むため）
- 負荷ツール：oha
- バックエンド：Clojure（ring-jetty）。Jetty は1リクエストをスレッド1本が最後まで担当する

### 2.2 バックエンドの設定

| 項目 | 値 | 意味 |
|---|---|---|
| `WORKERS` | 4 | 1台あたりの枠（リクエストを処理できるスレッド）の数 |
| `/big?kb=4096` | 4MB の返事 | 遅いクライアントにスレッドを拘束させる |
| `/slow?ms=50` | 50ms かけて返す | 普通のリクエストの代わり |
| `/slow?ms=3000` | 3秒かけて返す | 重いリクエストの代わり |
| `/session` | セッションでアクセス回数を数える | `SESSION_STORE` が `memory` ならプロセスのメモリ、`redis` なら Redis に置く |
| `/stats`（管理用ポート 9100） | 枠の使用数など | 本体の枠が埋まっていても見られるよう、別のスレッドプールで返す |

`/stats` の項目：`busy`（使用中の枠）、`handler`（ハンドラの中＝計算中の数。`busy` との差が返事の書き込みで拘束されている数）、`queued`（枠が空くのを待っている数）、`done`（処理し終えた件数）。

### 2.3 ソケットのバッファ

api、client、proxy の各コンテナで、ソケットのバッファの上限を 256KB に絞った（`sysctls`）。Linux の既定では数 MB まで育ち、4MB 程度の返事をほぼ吸収してしまい、「バッファに入りきらない大きな返事」の状況を作れないため。

（proxy コンテナは当初絞り忘れており、Step 2 の途中で追加した。経緯は 3.2 と 4.3 に記す。）

### 2.4 遅いクライアント

`curl --limit-rate 256k` で受信速度を毎秒 256KB に制限し、`/big?kb=4096`（4MB）を繰り返しダウンロードさせた（`slow-clients.sh`、4並列）。4MB を 256KB/s で受け取ると約16秒かかる。

### 2.5 nginx の設定（`nginx/day2.conf`）

| ポート | 裏のサーバ | 方式 |
|---|---|---|
| 8001 | api-a | `proxy_buffering on`（既定） |
| 8002 | api-a | `proxy_buffering off` |
| 8003 | api-a, b, c | ラウンドロビン（既定） |
| 8004 | api-a, b, c | `least_conn` |
| 8005 | api-a, b, c | `ip_hash` |

`worker_processes 1`（ラウンドロビンの順番や接続数をプロセスごとに数えないようにするため）。

### 2.6 手順

| Step | 内容 |
|---|---|
| 1 | api-a に直接。遅いクライアント1人での枠の拘束時間（1-2）、遅いクライアントなしの性能（1-3）、遅いクライアント4人を混ぜた性能（1-4）を測る。oha は `-z 15s -c 10`（1-4 は `-t 5s` も） |
| 2 | nginx 経由で同じ測定。遅いクライアントなし（2-1）、バッファリングあり（2-2）、なし（2-3） |
| 3 | 3件に1件だけ重いリクエスト（3秒）を送る（`periodic.sh`、60件、1件ごとに0.2秒）。ラウンドロビン（3-2）と `least_conn`（3-3）で比べる |
| 4 | Cookie を持ち回って `/session` を6回呼ぶ（`session.sh`）。ラウンドロビン（4-1）、`ip_hash`（4-2）、`ip_hash` に oha で負荷（4-3）、Redis に外出ししてラウンドロビン（4-4） |

## 4. 考察

### 4.1 捌ける数は「枠の数 ÷ 占有時間」で決まり、CPU では決まらない

1-3 の 78.79 件/秒は、枠4本 ÷ 1件 50ms ＝ 80件/秒の見積もりとほぼ一致した。p50 が 50ms ではなく 152ms になったのは、同時に10本送っているのに枠が4本しかなく、常に6本前後がキューで待っていたためである。リトルの法則で見積もると、10本 ÷ 80件/秒 ≈ 125ms で、実測とおおむね合う。2-2 の `/stats` の `queued=6` は、この6本を直接見たものである。

1-4 の 2.33 件/秒は、事前チェックで計算した「枠4本 ÷ 1件約2秒 ≈ 毎秒2件弱」とほぼ一致した。このとき api-a の CPU は約2%しか使われていなかった。1-2 の `handler=0`、`busy=1` から、スレッドは計算ではなく、遅いクライアントへの**返事の書き込み**で拘束されていたことがわかる。CPU を速くしても増やしても、この状況は改善しない。

### 4.2 バッファに入りきった分は、スレッドが待たなくてよい

1-2 で、スレッドが拘束されたのは約13秒で、ダウンロード全体（約16秒）より約3秒短かった。256KB/s で3秒分は約 768KB で、絞った送信バッファ（256KB）と受信バッファ（256KB）などの合計とおおむね合う。アプリの書き込みはソケットのバッファに入れ終わった時点で完了し、その後の送り届けは OS が引き受ける。遅いクライアントが枠を拘束するのは、返事がバッファに入りきらないほど大きいときである。

### 4.3 nginx のバッファリングは、遅いクライアントの相手を引き受ける

proxy のバッファを絞った後の比較で、バッファリングの有無による差がはっきり出た。

| | Requests/sec | 成功率 | 枠を埋めていたもの |
|---|---|---|---|
| 1-4 直接 | 2.33 | （タイムアウトあり） | 遅いクライアントへの書き込み |
| 2-2 バッファリングあり | 78.12 | 100% | 普通のユーザーの計算（`handler=4`） |
| 2-3 バッファリングなし | 20.46 | 93.27% | 遅いクライアントへの書き込み（`handler=0`） |

2-2 では、遅いクライアントが4人いても、いないとき（2-1 の 79.19 件/秒）とほぼ同じだけ捌けた。nginx が 4MB の返事を一気に受け取って溜めるので、api-a は書き込みに時間を使わず（`/big` の件数がほとんど増えない）、枠は普通のユーザーの計算だけに使われた（`handler=4`）。これは時代③の「待つ仕事を前段に引き取らせ、アプリを本業に専念させる」の実例である。nginx を置くこと自体ではなく、**nginx が返事を丸ごと受け止めること**が効いている。

2-3 の `/stats` では、`handler=0` のまま `busy=4/4` が続き、普通のユーザーは `queued` で待ち続けた。遅いダウンロードが一斉に終わった隙間だけ `/slow` が一気に進む、という動きを繰り返した。1-4 より数字が良かった（20.46 件/秒）のは、遅いダウンロードの終わるタイミングと測定期間の重なり方の違いと考えられるが、仕組みは 1-4 と同じである。

**途中で見つかった穴**：proxy コンテナのバッファを絞る前は、2-3（バッファリングなし）でも 49.06 件/秒出ていた。nginx のコンテナのソケットのバッファが既定の大きさ（数 MB まで育つ）のままで、`proxy_buffering off` でも OS のバッファが返事の大部分を溜めていたためと考えられる。絞った後に 20.46 件/秒まで下がったことが、この説明を支持している。逆に言えば、**返事を丸ごと受け止められる場所が経路のどこか1か所にあれば、アプリの枠は解放される**。それが nginx のバッファでも、OS のソケットのバッファでも、仕組みは同じである。

なお、`du -sh` で一時ファイルの置き場所がほぼ空（36.0K）に見えたのは、nginx が一時ファイルを作った直後にファイル名を消し、開いたファイルの中身だけを使い続けるためである。

### 4.4 ラウンドロビンは回数を、least_conn は仕事の量を均等にする

3-2 のラウンドロビンでは、3の倍数番目の重いリクエストが、順番通り全部 api-c に届いた。api-c は枠が満杯のうえキューに1〜2件が待ち続け、その間 api-a と api-b の枠は一度も使われなかった。3台合わせて12本の枠があるのに、使われたのは4本だけだった。重いリクエストが届く速さ（毎秒約1.5件）が、1台が捌ける速さ（4本 ÷ 3秒 ≈ 毎秒1.33件）を上回ったためにキューができた。

3-3 の `least_conn` では、どのサーバも `busy` は最大2本で、キューは一度も出なかった。`least_conn` はリクエストの重さを知らないが、重い処理は返事が返るまで接続を握り続けるので、「処理中の接続の数」に重さが表れる。nginx はその数を見て新しいリクエストを避けるので、重い処理が分散した。一方、処理した件数は 8・11・36 と偏った。重いリクエストを抱えていないサーバに、軽いリクエストが集まったためと考えられる。

| | 配る回数 | 仕事の量 | 結果 |
|---|---|---|---|
| ラウンドロビン | 均等 | 偏る（重いものが全部 c） | c だけ詰まる |
| least_conn | 偏る | 均等（どこも最大2本） | どこも詰まらない |

ただし、`least_conn` は間接的な指標であり、壊れていて即座にエラーを返すサーバは接続数が少なく見えるため、かえって多く送られてしまう（Day 3 に関係）。

### 4.5 セッションは「同じサーバに送る」ではなく「どのサーバも同じにする」で直す

4-1 のラウンドロビンでは、6回が3台に2回ずつ配られた。メモリ上のセッションはそのサーバの中にしかないので、別のサーバに当たるたびに新しいセッションが作られ、Cookie のセッション ID も上書きされる。一度別のサーバに当たると、元のサーバに戻っても元のセッションは引き継がれない。

4-2 の `ip_hash` では、6回とも同じサーバに届き、セッションは保たれた。しかし 4-3 で、client コンテナという1つの IP からの負荷が全部 api-a に集まり、api-a は満杯（`queued=6`）、b と c は何もしていなかった。これは、大学や会社の NAT の後ろにいる大勢のユーザー、あるいは nginx の手前に ALB や Cloudflare がいる構成（nginx から見た接続元が全員そのプロキシの IP になる。Day 1 参照）で起きることと同じである。さらに、そのサーバが落ちればセッションも失われる。`ip_hash` は症状を隠しただけで、「セッションが1台のサーバの中にしかない」という原因は残っている。

4-4 で、セッションを Redis に外出しすると、ラウンドロビンで a, b, c と配られても `count` は 1 から 6 まで途切れずに増えた。どのサーバも同じセッション ID で同じデータを引けるので、**サーバが状態を持たなくなり**、負荷分散の方式を自由に選べるようになる。代わりに、Redis が新しい依存先（落ちたら全員のセッションが使えなくなる場所）になる。

| 方式 | セッション | 負荷の配り方 | 残る問題 |
|---|---|---|---|
| ラウンドロビン＋メモリ | 消える | 均等 | ログインが保てない |
| ip_hash＋メモリ | 保てる | 1つの IP からは全部同じ1台 | NAT やプロキシの後ろで偏る。サーバが落ちるとセッションも消える |
| ラウンドロビン＋Redis | 保てる | 均等 | Redis が新しい依存先になる |

## 5. 結論

1. 1リクエスト1スレッドのサーバの捌ける数は、「枠の数 ÷ 1リクエストが枠を占有する時間」で決まる。遅いクライアントへの返事の書き込みで占有時間が延びると、CPU が約2%しか使われていなくても、捌ける数は約80件/秒から約2件/秒まで落ちた
2. 遅いクライアントが枠を拘束するのは、返事がソケットのバッファに入りきらないときである。経路のどこかに返事を丸ごと受け止める場所があれば、アプリの枠は解放される
3. nginx のバッファリングは、まさにその受け止め役である。遅いクライアントが4人いても、バッファリングありでは約78件/秒（成功率100%）、なしでは約20件/秒（成功率93%）だった
4. ラウンドロビンは配る回数を均等にするが、仕事の量は均等にしない。重さの違うリクエストが混ざると、1台だけ詰まって残りが暇になる。`least_conn` は処理中の接続の数を通して重さを間接的に見るので、仕事の量が均等になった
5. 台数を増やすとメモリ上のセッションは消える。`ip_hash` で同じサーバに送り続けると、1つの IP の後ろにいる大勢が1台に集まる。セッションを Redis に外出しして、サーバが状態を持たないようにするのが根本的な解決である
