# Day 6 レポート — 人気の記事にアクセスが集中した

## 1. 目的

### 1.1 背景（どの時代の困りごとか）

- **時代①（Web が重くなる）**：同じページを大勢が見るなら、手前で一度作った返事を覚えておけば、裏のサーバまで届けずに済む。Squid の httpd accelerator のような、リバースプロキシの原型となったキャッシュ

### 1.2 確かめたいこと

1. プロキシのキャッシュで、アプリに届く数と捌ける数はどう変わるか
2. キャッシュは、いつ作られ、いつ使われ、いつ作り直されるか
3. キャッシュが切れた瞬間の殺到は起きるか、どう抑えるか
4. 見る人によって中身が変わるページをキャッシュすると、何が起きるか

---

## 2. 手法

### 2.1 構成（`compose.day6.yml`）

```
client ──→ proxy(nginx: 8401〜8404) ──→ api-a(枠 8本、描画 200ms)
```

### 2.2 アプリ（`server.clj` の `article`）

- `GET /articles/:id`：描画に 200ms かかる記事ページ。「ログイン中: 名前」を Cookie の `user` から表示する
- どの返事にも `Cache-Control: public, max-age=10`（誰にでも10秒使い回してよい）を付ける。見る人によって中身が変わるのにこう付けているのが、Step 4 の事故の原因
- `/stats` の `renders`：記事ごとの描画回数（＝アプリまで届いた回数）

### 2.3 nginx の入口（`nginx/day6.conf`）

| ポート | 中身 |
|---|---|
| 8401 | キャッシュなし |
| 8402 | キャッシュあり（`proxy_cache` だけ。キーは既定の URL、期限はアプリの `Cache-Control` に従う） |
| 8403 | 8402 ＋ `proxy_cache_lock`、`proxy_cache_use_stale updating`、`proxy_cache_background_update` |
| 8404 | 8403 ＋ `proxy_cache_bypass $cookie_user`、`proxy_no_cache $cookie_user` |

### 2.4 手順

| Step | 内容 |
|---|---|
| 1 | 8401 と 8402 に、20本同時で10秒間（oha） |
| 2 | 8402 に1件、もう1件、11秒待って1件。`X-Cache-Status` を見る |
| 3 | 8402 と 8403 に、50本同時で25秒間 |
| 4 | 8402 と 8404 で、`user=yamada`、`user=sato`、Cookie なし（ゲスト）の順に開く |

## 4. 考察

### 4.1 キャッシュは、アプリの枠の上限から解放する

キャッシュなしでは、枠8本 ÷ 描画 200ms ＝ 毎秒40件の上限どおりだった。キャッシュありでは約200倍の毎秒8124件を捌き、描画は約20分の1になった。8124 という値は、nginx と負荷ツールが同じ PC の中で動く速さで決まっており、アプリについての意味はない。読み取るべきは、アプリに届く回数がリクエストの数ではなく「キャッシュが空のときに来た数」で決まるようになったことである。

描画が1回ではなく20回だったのは、最初の1本が描画している 200ms の間に残りの19本も来て、キャッシュがまだ空だったためである。これは、キャッシュスタンピードの小さな版である。

### 4.2 キャッシュの期限は「古さの許容範囲」

HIT の返事は描画した時刻が変わらず、中身は最大10秒前のままだった。期限（アプリの `max-age=10`）は、どれだけ古い内容を見せてよいかの許容範囲であり、それを決めているのはアプリである。

### 4.3 期限切れの殺到は、nginx の設定で抑えられる

素朴なキャッシュでは、キャッシュが空になるたびに、その瞬間に来ていた約50本がまとめてアプリに届き、25秒で100回描画した。3行の設定を足すと、3回（最初と期限切れごとに1回ずつ）になった。

- `proxy_cache_lock`：キャッシュが空のとき、1本だけをアプリに送り、残りは待たせる
- `proxy_cache_use_stale updating`：更新中は、他の人に古い返事を返す
- `proxy_cache_background_update`：最初に気づいた人にも古い返事を返し、更新は裏で行う

古い返事を返す分、許容範囲はさらに描画1回分延びる。記事のように数秒古くても困らない内容だから使える。Redis 実践編ではアプリの中で対策を書いたが、プロキシのキャッシュでは設定で済む。

### 4.4 「全員に同じ返事でよいか」を間違えると、黙って事故が起きる

8402 では、佐藤さんに山田さんのページが表示された。キャッシュキーは URL だけで Cookie を含まないので、nginx から見て2人は同じリクエストであり、アプリが `public` を付けたので nginx は誰にでも使い回した。エラーにならないので、指摘されるまで気づきにくい。

8404 では、Cookie に `user` がある人にはキャッシュを使わず（BYPASS）、それぞれ正しいページが表示された。対策の置き場所は複数ある。

| 対策 | 担当 | 弱点 |
|---|---|---|
| Cookie があれば素通り（8404） | nginx | ログイン中の人はキャッシュの恩恵がない。Cookie の名前が変わると再発する |
| ログイン中なら `Cache-Control: private` | アプリ | 全員がこの約束を守る必要がある |
| 記事本体と「その人だけの部分」（`/me`）を分ける | アプリ | 作りが複雑になる |

中身を知っているアプリが正しい `Cache-Control` を返すことを基本にし、nginx の設定は安全装置として重ねるのがよい。

### 4.5 事後チェックで分かったこと

- **キャッシュキーからクエリ文字列を外すと**、`/search?q=nginx` と `/search?q=redis` が同じキーになり、他人の検索結果が表示される。キーには「返事の中身を変えるもの」をすべて含める。逆に、`?utm_source=...` のような中身を変えないものを含めると、別々に覚えて HIT しにくくなる
- **`proxy_ignore_headers Set-Cookie` で `Set-Cookie` 付きの返事もキャッシュすると**、期限の間に来た全員に同じセッション ID が配られる。誰かがそのままログインすると、全員がその人としてログインした状態になり、なりすましができる。nginx が既定でこれをキャッシュしないのはこのためで、キャッシュしたいページではアプリが Cookie を発行しないようにする

### 4.6 パターンの整理

**キャッシュの仕方**

| パターン | 利点 | 欠点 |
|---|---|---|
| キャッシュなし | いつも最新。事故がない | 全リクエストがアプリに届く |
| 素朴なキャッシュ | 設定1行でアプリに届く数が激減する | 期限切れのたびに殺到。アプリの `Cache-Control` の誤りがそのまま事故になる |
| ＋殺到を抑える | 期限切れでもアプリに届くのは1回。誰も待たない | さらに描画1回分古い内容を見せる |
| マイクロキャッシュ（期限1秒程度） | 古さは最大1秒。殺到の瞬間を吸収する | アクセスが少ないとほとんど効かない |
| アプリの中でキャッシュ（Redis） | 返事の一部だけを覚えられる | リクエストはアプリまで届き、枠は使う |

**nginx の設定ごとの on/off**

| 設定 | 効く場面 | on にすると |
|---|---|---|
| `proxy_cache_lock` | 空のキャッシュに同時に来たとき | 1本だけアプリに届く |
| `proxy_cache_use_stale updating` | 期限切れに同時に来たとき | 更新中は他の人に古い返事 |
| `proxy_cache_background_update` | 期限切れに最初に気づいた人 | その人にも古い返事。更新は裏で（`use_stale updating` がないと働かない） |
| `proxy_cache_bypass $cookie_user` | ログイン中の人が来たとき | キャッシュから返さない |
| `proxy_no_cache $cookie_user` | ログイン中の人への返事 | 覚えない |
| `proxy_ignore_headers Set-Cookie` | `Set-Cookie` 付きの返事 | 覚える（なりすましの危険） |

**一緒に使う前提の2つ組：bypass と no_cache**

| | `no_cache` なし | `no_cache` あり |
|---|---|---|
| `bypass` なし | 他人のページが見える（Step 4） | ログイン中の人に、キャッシュされたゲストのページ |
| `bypass` あり | ログイン中の人の返事を覚えてしまい、次のゲストに他人のページ | 正しい（8404） |

「キャッシュから返さない」と「キャッシュに覚えない」は別の判断なので、必ずセットで書く。殺到を抑える3つと、ログイン中の人の扱いの2つは、効く場面が違うので互いに影響しない。

---

## 5. 結論

1. プロキシのキャッシュで、アプリに届く数はリクエストの数ではなく「キャッシュが空のときに来た数」で決まるようになり、捌ける数は約200倍、描画は約20分の1になった
2. キャッシュの期限は、古い内容を見せてよい許容範囲であり、アプリの `Cache-Control` が決める
3. 期限切れのたびに、同時に来ていたリクエストがまとめてアプリに届く（25秒で100回）。`proxy_cache_lock`・`proxy_cache_use_stale updating`・`proxy_cache_background_update` で、3回に抑えられた
4. 見る人によって中身が変わるページを、「誰にでも使い回してよい」としてキャッシュすると、他人の情報が黙って表示される。同じ仕組みで、`Set-Cookie` をキャッシュするとなりすましが起きる。「全員に同じ返事でよいか」をアプリが正しく伝え、nginx は安全装置を重ねる
