# Day 4 レポート — 止めずに新しいバージョンを出したい

## 1. 目的

### 1.1 背景（どの時代の困りごとか）

- **時代④（マイクロサービス）**：サービスを独立して頻繁にデプロイするようになり、入れ替えの瞬間のエラーや、新しい版を一気に出すリスクが問題になった。手前のプロキシは、裏の入れ替えをクライアントから隠し、向き先や割合を制御できる

### 1.2 確かめたいこと

1. 負荷がかかったままサーバを入れ替えると、どのリクエストが失敗するか
2. グレースフルシャットダウンで、それを防げるか
3. Blue-Green、カナリア、ミラーリングは、それぞれどう動き、何に注意が要るか

---

## 2. 手法

### 2.1 構成（`compose.day4.yml`）

```
client ──→ proxy(nginx: 8201〜8204) ──→ api-a(旧版 v1) / api-b(新版 v2)
```

### 2.2 仕組みの分担

| やっていること | 担当 | どこに書いてあるか |
|---|---|---|
| SIGTERM を受けたら、新しい接続を断り、処理中のリクエストを終えてから止まる | アプリ | `server.clj` の `-main`（`GRACEFUL=true` のときだけ） |
| 拒否された接続を、別のサーバで送り直す | nginx | 既定の `proxy_next_upstream`（Day 3 と同じ） |
| 設定を読み直すとき、処理中のリクエストを切らない | nginx | `nginx -s reload` |
| 向き先を切り替える | nginx | `day4-active/upstream.conf` の1行を書き換えて reload |
| 一部だけ新版に流す／リクエストを複製する | nginx | `weight` と `mirror` |

### 2.3 nginx の設定（`nginx/day4.conf`）

| ポート | 設定 |
|---|---|
| 8201 | api-a と api-b にラウンドロビン |
| 8202 | 向き先を `upstream.conf` の1行で決める（Blue-Green） |
| 8203 | `weight` で api-a に9、api-b に1（カナリア） |
| 8204 | 返事は api-a から、複製を api-b にも送る（ミラーリング） |

### 2.4 手順

| Step | 内容 |
|---|---|
| 1 | `GRACEFUL=false`。8201 に `POST /slow?ms=2000` を8並列で20秒送り続け、途中で `docker compose restart api-b` |
| 2 | `GRACEFUL=true`（Docker の猶予期間も30秒）で、Step 1 と同じ |
| 3 | 8202 に0.5秒ごとに GET を送りながら、向き先を api-a → api-b → api-a に切り替える（書き換えて `nginx -s reload`） |
| 4 | 8203 に GET を30回。8204 に POST を1回送り、両方のログを見る |

POST を使ったのは、送った後に失敗しても nginx がやり直さないため、切られたリクエストがそのまま 502 としてユーザーに見えるからである。

## 3. 結果

### 3.1 Step 1, 2：入れ替え

| | SIGTERM の時点で処理中（`in-handler`） | 200 | 502 | api-b のログ |
|---|---|---|---|---|
| Step 1 `GRACEFUL=false` | 4 | 68 | 4 | `SIGTERM received` の直後に終了（exit 143） |
| Step 2 `GRACEFUL=true` | 4 | 72 | 0 | `SIGTERM received` の後、`POST /slow ... -> 200` が4行、続いて `stopped` |

### 3.2 Step 3：Blue-Green

返事の版は、`v1` が6回、切り替え後に `v2` が14回、戻した後に `v1` が2回と並んだ。エラーや空の返事はなかった。

### 3.3 Step 4：カナリアとミラーリング

- カナリア（8203、30回）：`v1` が27回、`v2` が3回
- ミラーリング（8204、POST 1回）
  - 1回目：返事は api-a（v1）から。api-a のログには `POST /slow` があったが、api-b にはなかった。nginx のログに `no resolver defined to resolve api-b ... subrequest: "/_mirror"`
  - 設定を直した後：api-a と api-b の両方のログに `POST /slow ... -> 200`

## 4. 考察

### 4.1 入れ替えで失敗するのは「処理中」のリクエストだけ

Step 1 で、SIGTERM の時点で処理中だった件数（4件）と、ユーザーに返った 502 の件数（4件）が一致した。処理中のリクエストはプロセスごと消され、接続が途中で切られた。リクエストはすでに api-b に届いているので、nginx は POST をやり直さず、そのまま 502 を返した（Day 3 の「送った後の失敗」と同じ）。

一方、api-b が止まっている間に届いた新しいリクエストは、接続の段階で拒否され、nginx が api-a でやり直したので、エラーにならなかった（Day 3 の「送る前の失敗」と同じ）。入れ替えの問題は、処理中のリクエストに絞られる。

### 4.2 グレースフルシャットダウンはアプリの仕事

Step 2 では、SIGTERM の時点で処理中だった4件が最後まで処理されてから止まり、502 は0件になった。

効いたのは、アプリ（Jetty）の次の設定である。

```clojure
(when graceful?
  (.setHandler server (doto (StatisticsHandler.) (.setHandler (.getHandler server))))  ; 処理中の数を数える
  (.setStopTimeout server 30000)     ; 止めるときに、処理中が終わるのを最大30秒待つ
  (.setStopAtShutdown server true))  ; SIGTERM を受けたら、この手順で止める
```

SIGTERM を受けると、Jetty は新しい接続の受け付けをやめ、処理中のリクエストが終わるのを待ってから止まる。新しい接続が拒否されるので、nginx は別のサーバでやり直せる。nginx 側に特別な設定は要らず、**アプリが「受け付けをやめる → 待つ → 止まる」の順を守ること**と、**nginx が拒否された接続をやり直すこと**の組み合わせで、エラーが0になった。

アプリの待ち時間（30秒）は、Docker の猶予期間（`stop_grace_period`、既定10秒）以下である必要がある。待っている途中で SIGKILL が来ると、結局切られてしまう。

### 4.3 Blue-Green は「戻すのが速い」

向き先の1行を書き換えて reload するだけで、切り替えも戻しも瞬時に起き、エラーもなかった。`nginx -s reload` は、新しい設定で新しいワーカーを起動し、古いワーカーには処理中のものを終えてから止まらせるので、reload 自体ではリクエストが切れない。

旧版を動かしたままにしておくので、新版に問題があればすぐ戻せる。代わりに、2つの版を同時に動かす資源が要り、切り替えは全員一斉なので、戻すまでの間は全員が影響を受ける。

### 4.4 カナリアは影響を一部に絞る

`weight` 9:1 で、30回中3回が新版に届いた。新版に問題があっても、影響はリクエストの1割に絞られる。ただし `weight` はリクエスト単位の割り振りなので、同じユーザーが v1 と v2 を行き来する。ユーザー単位で固定したい場合は `split_clients` を使う。

### 4.5 ミラーリングはデータを変える操作に弱い

ミラーリングでは、1回の POST が旧版と新版の両方で処理され、ユーザーには旧版の返事だけが返った。新版を本番と同じリクエストで、ユーザーに影響を与えずに試せる。しかし、これが注文を作る POST で、両方の版が同じデータベースを使っていれば、注文が黙って二重になる（Day 3 の 3-2 と同じ）。複製は GET に限るか、新版を試験用のデータベースにつなぐ必要がある。

### 4.6 途中で見つかった問題：変数を含む proxy_pass と名前の解決

最初、ミラー先を `proxy_pass http://api-b:3000$request_uri;` と書いていた。`$request_uri` のような変数を含む `proxy_pass` では、nginx は起動時ではなくリクエストのたびに名前を IP に変換しようとし、そのための `resolver` の設定が必要になる。設定がなかったため、複製は送られず（`no resolver defined`）、ユーザーへの返事には影響がないので、ログを見るまで気づかなかった。

`upstream mirror_target { server api-b:3000; }` として名前を付け、`proxy_pass http://mirror_target$request_uri;` と書き直すと、`api-b` は起動時に一度だけ変換されるようになり、複製が届いた。

事前の確認では、Docker を使えなかったため `api-b` を IP アドレスに置き換えて試しており、名前の変換が不要だったのでこの問題が表に出なかった。ミラーリングは失敗してもユーザーに見えないので、複製先のログで届いていることを確かめる必要がある。

---

## 5. 結論

1. 負荷がかかったままサーバを入れ替えると、失敗するのは処理中だったリクエストだけで、件数は SIGTERM の時点で処理中だった数と一致した（4件中4件が 502）
2. アプリがグレースフルシャットダウン（受け付けをやめる → 処理中を待つ → 止まる）をすると、nginx が新しいリクエストを別のサーバに送り直すので、エラーは0件になった。これはアプリの仕事で、待ち時間は Docker の猶予期間以下にする
3. Blue-Green は向き先の1行を変えて reload するだけで、瞬時に切り替え・戻しができる。全員一斉に切り替わる点が弱い
4. カナリアは新版への影響を一部に絞れる。ミラーリングは新版を本番のリクエストで試せるが、データを変える操作を複製すると二重に処理される

### 残った課題

- `nginx -s reload` の最中に、処理中のリクエストが切れないことは未計測
