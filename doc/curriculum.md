# リバースプロキシ実践カリキュラム（nginx / Clojure / Day 0＋9日）

> **ゴール**: 「リバースプロキシとは何か」「なぜ間に1枚挟むのか」を、自分の困りごとに当てはめて説明できるようになる。業務の Ingress や自宅サーバの Cloudflare 構成を見たときに、「ここで何が起きているか」を読み解けるようにする。
> **形式**: Kafka 実践編と同じく、利用場面（課題）ごとに1日1テーマ。毎日違う場面を扱う。
> **自作の判断**: 全日程の終了後に、Clojure でリバースプロキシを自作する価値があるかを判断する。

---

## Day 0 の結論（振り返り用）

**リバースプロキシとは、サーバ群の手前に立つ「代理の窓口」。クライアントからの接続をいったん自分が受け取り、中身を見たうえで、裏のサーバへ改めて取り次ぐ。**

- 仕組みは1つ（全リクエストが必ず1か所を通り、そこで中身を見て、手を加え、行き先を選べる）。そこから多くの利点が出てくる
- 接続が「クライアント⇄プロキシ」「プロキシ⇄バックエンド」の2本に分かれるので、**利点と副作用は同じ根っこから出る**（クライアントIPやスキームが見えなくなる、リトライで二重処理が起きる、など）

| 時代 | 困りごと | 生まれたもの |
|---|---|---|
| ① 1990年代 Webが重くなる | 台数を増やすとどこにつなぐか問題。DNSラウンドロビンは障害に反応できず偏る | ロードバランサ、リバースプロキシキャッシュ（判断を「名前を引くとき」→「リクエストが来るとき」へ） |
| ② SSLの普及 | 暗号処理が重い。暗号化されると中身が見えない | TLS終端 → L7での振り分け |
| ③ C10K問題 | 待ち時間でプロセスの枠が埋まる（CPUではない） | イベント駆動の nginx を前に置き、待つ仕事を引き取る |
| ④ マイクロサービス | 入口が散らかる、住所が変わり続ける、サービス間の通信が壊れやすい | APIゲートウェイ、Ingress、サイドカー（Envoy）、サービスメッシュ |
| ⑤ ゼロトラスト | 「内側だから安全」が成り立たない | アクセスプロキシ、入口での認証、mTLS |

**Day 0 の残り**: Step 5（総合の理解度チェックとレポート作成）

## Day 1 — 自宅サーバで、複数のアプリを1つの入口から公開したい

**場面**: 自宅サーバに API（Clojure）が2つと、フロント（静的ファイル）がある。今はそれぞれのポートを直接公開していて、フロントから API を呼ぶと CORS エラーになる。いしなび（フロントは GitHub、API は Cloud Run の別ドメイン）と同じ構図。

**時代**: ①（住所と機械の切り離し）、②（TLS終端）、④（パスでの振り分け）

**深く理解したいこと**: プロキシを挟むと、アプリから見える接続元・ホスト名・スキームがどう変わるか

**ステップ**
1. **環境構築と素朴な構成**：共通バックエンドと Docker Compose を用意する。アプリを直接ポート公開し、別オリジンからの呼び出しで CORS エラーを再現する
2. **振り分けと静的配信**：nginx でパス（`/api/a`、`/api/b`）とホスト名で振り分け、フロントは nginx から直接返す。同一オリジンになって CORS が消えることを確認する。`/whoami` で、アプリから見える接続元IPと `Host` がどう変わるかを見る
3. **TLS終端**：mkcert で証明書を作り、nginx で https を受ける。アプリの「http なら https へリダイレクト」でリダイレクトループを再現し、`X-Forwarded-Proto` で直す
4. **L4 と L7 の比較**：同じ振り分けを nginx の `stream`（L4）で試し、パスでは振り分けられないこと、アプリから見える情報が違うことを確かめる
5. **事後チェックとレポート**

**事前チェックの論点**: 同一オリジンとは何か、なぜプロキシで CORS が消えるのか / L4 と L7 で見える情報の違い

**事後チェックの例**: `proxy_pass` の末尾に `/` を付けたら付けなかったらどうなるか / `Host` ヘッダーを書き換えないとアプリにはどう見えるか

**チェックポイント**
- [ ] 1つの入口（443）から、2つの API とフロントにアクセスできる
- [ ] リダイレクトループを再現し、直せた
- [ ] 自宅サーバの Cloudflare 構成で、同じことがどこで起きているか説明できる

## Day 2 — アクセスが増えて、1台では捌けなくなった

**場面**: アプリへのアクセスが増え、応答が遅くなった。CPU には余裕があるのに、なぜか新しいリクエストが待たされる。台数を増やしたら、今度はログイン状態が勝手に消える。

**時代**: ①（スケールアウト）、③（遅いクライアントと枠）

**深く理解したいこと**: 「捌ける数 ＝ 枠の数 ÷ 占有時間」を実測で確かめる。分散方式によって偏りが生まれる理由

**ステップ**
1. **1台の限界を測る**：Jetty のスレッド数を少なくした1台に、遅いクライアント（`curl --limit-rate`）を混ぜて負荷をかける。CPU は空いているのに詰まることを確認する
2. **nginx のバッファリングの効果**：nginx を前に置き、`proxy_buffering` の on/off で同じ計測をする（Day 0 の Q2 の実測）
3. **3台に分散する**：`/slow` が混ざる負荷で、ラウンドロビンと `least_conn` の応答時間とインスタンスごとの偏りを比べる
4. **セッションが消える**：`/session` で回数が飛ぶことを確認する。`ip_hash`（sticky）と、セッションを Redis に外出しする方法を比べる
5. **事後チェックとレポート**

**事前チェックの論点**: 枠の占有時間とは何か / ラウンドロビンが偏るのはどんなときか / sticky の弱点

**事後チェックの例**: 1台だけ極端に遅くなったら、各方式はどう振る舞うか / `ip_hash` で大半のユーザーが同じ NAT の後ろにいたらどうなるか

**チェックポイント**
- [ ] バッファリングの有無で、捌ける数がどれだけ変わるかの実測値がある
- [ ] 分散方式ごとの偏りを数字で説明できる

## Day 3 — 裏のサーバが1台落ちた・遅くなった（一番深く）

**場面**: 3台のうち1台が落ちた、または詰まった。一部のユーザーにエラーが出る。リトライを入れたら、今度は注文が二重にできた。

**時代**: ①（障害への反応）、④（リトライの増幅）

**深く理解したいこと**: プロキシはいつ「失敗」と判断し、何をするのか。リトライが安全なのはどんなときか

**ステップ**
1. **落ちたサーバを外す**：1台を止め、nginx のパッシブヘルスチェック（`max_fails`、`fail_timeout`）と `proxy_next_upstream` の挙動を観察する。検知までの間にエラーが何件出るかを数える
2. **詰まったサーバに引きずられない**：`/slow` で詰まらせ、タイムアウト（`proxy_connect_timeout`、`proxy_read_timeout`）の有無で全体の応答時間を比べる。アクセスログに `$request_time` と `$upstream_response_time`、リクエストIDを出して、遅延がどこで生じたかを切り分ける
3. **二重注文**：`POST /orders` を「処理は成功するが返事が遅い」状態にし、POST もリトライする設定で二重注文を再現する。冪等キー（`Idempotency-Key`）をアプリに実装して防ぐ
4. **リトライストーム**：nginx を2段にして（nginx → nginx → アプリ）、各段でリトライさせる。`/flaky` が失敗し続けるときにアプリに届く回数を数え、掛け算になることを確かめる
5. **事後チェックとレポート**

**事前チェックの論点**: 「接続できない」と「返事が来ない」の違い / 冪等とは何か、GET と POST で何が違うか / リトライの増幅

**事後チェックの例**: `proxy_read_timeout` をアプリの処理時間より短くしたらどうなるか / nginx が POST を既定でリトライしないのはなぜか、`non_idempotent` を付けたら何が起きるか / 冪等キーの保存期間が切れた後に同じキーが来たらどうなるか

**チェックポイント**
- [ ] 1台停止時のエラー件数と、設定変更による変化の実測値がある
- [ ] 二重注文を再現し、冪等キーで防げた
- [ ] リトライの回数が段数の掛け算になることをログで確認した

## Day 4 — 止めずに新しいバージョンを出したい（浅め）

**場面**: デプロイのたびに数秒エラーが出る。新バージョンを全員に一気に出すのも怖い。

**時代**: ④

**ステップ**
1. **素朴な切り替え**：負荷をかけたままコンテナを入れ替え、失敗したリクエストの件数を数える
2. **graceful に切り替える**：nginx の設定リロード（`nginx -s reload`）で処理中のリクエストが落ちないことを確認する。アプリ側も SIGTERM を受けたら処理中のリクエストを終えてから止まるようにする
3. **Blue-Green**：upstream を切り替えて、旧版から新版へ一瞬で移す
4. **カナリアとミラーリング**：重み付け（`weight` / `split_clients`）で新版に少しだけ流す。`mirror` で本番のリクエストを複製して新版に送る
5. **事後チェックとレポート**

**事前チェックの論点**: 処理中のリクエストは切り替えの瞬間にどうなるか / Blue-Green とカナリアの違い

**事後チェックの例**: ミラーリングで POST を複製したら何が起きるか

**チェックポイント**
- [ ] 素朴な切り替えと graceful な切り替えで、失敗件数の差を実測した

## Day 5 — リアルタイム通知を通したい（長時間・大容量の接続）

**場面**: SSE の通知が、直接アクセスなら届くのに、nginx 経由だとまとめて遅れて届く。WebSocket はつながらず、つながっても1分で切れる。大きなファイルをアップロードすると 413 エラーになる。

**時代**: ③（接続の扱い）

**ステップ**
1. **SSE が届かない**：nginx 経由でイベントがまとめて届く現象を再現し、バッファリングが原因であることを確かめる。`proxy_buffering off` や `X-Accel-Buffering` で直す
2. **切れる接続**：`proxy_read_timeout` で一定時間後に切れることを確認し、タイムアウトとハートビートで対処する
3. **WebSocket**：`Upgrade` / `Connection` ヘッダーと HTTP/1.1 の設定がないとつながらないことを確認して直す
4. **大きなアップロードと接続の再利用**：413 を再現し、`client_max_body_size` とリクエストのバッファリングを調整する。upstream の `keepalive` の有無で、裏への接続数を比べる
5. **事後チェックとレポート**

**事前チェックの論点**: Day 2 で効いたバッファリングが、なぜ SSE では邪魔になるのか / WebSocket は HTTP とどう違うか

**事後チェックの例**: SSE の接続が1万本あったら、nginx とアプリそれぞれの何を消費するか

**チェックポイント**
- [ ] SSE、WebSocket、大きなアップロードが nginx 経由で動く
- [ ] 同じバッファリングが「助けになる場面」と「邪魔になる場面」を説明できる

## Day 6 — 人気の記事にアクセスが集中した

**場面**: SNS で記事が拡散され、描画の重い記事ページにアクセスが殺到した。キャッシュを入れたら、ログイン中のユーザー名が他人の画面に出た。

**時代**: ①（リバースプロキシキャッシュ）

**ステップ**
1. **素朴な構成で測る**：`/articles/:id` に集中アクセスをかけ、応答時間とアプリへの到達件数を測る
2. **プロキシでキャッシュする**：`proxy_cache` と `Cache-Control` を設定し、`$upstream_cache_status` で HIT / MISS を確認しながら同じ計測をする
3. **期限切れの瞬間の殺到**：キャッシュが切れた瞬間にアプリへリクエストが集中することを確認し、`proxy_cache_lock` と `proxy_cache_use_stale updating` で抑える（Redis 実践編のキャッシュの日と比較する）
4. **他人の情報が見える事故**：ログインユーザー向けの内容をキャッシュして事故を再現し、キャッシュキーの設計や Cookie があるときのバイパスで直す
5. **事後チェックとレポート**

**事前チェックの論点**: アプリ内キャッシュ（Redis）とプロキシのキャッシュの違い / 何をキャッシュしてはいけないか

**事後チェックの例**: キャッシュキーにクエリ文字列を含めないとどうなるか / `Set-Cookie` を返すレスポンスをキャッシュしたら何が起きるか

**チェックポイント**
- [ ] キャッシュの有無で、応答時間とアプリへの到達件数がどう変わるかの実測値がある
- [ ] 他人の情報が見える事故を再現し、直せた

## Day 7 — 悪意のあるアクセスや攻撃から守りたい（深め）

**場面**: 公開したアプリに、怪しいアクセスが来るようになった。IP 制限した管理画面に外から入られた形跡がある。1人のクライアントが叩きまくって全員が遅い。

**時代**: ③（slowloris）、⑤（入口で守る）

**注意**: 攻撃の再現は、自分のローカル環境に対してだけ行う

**深く理解したいこと**: 入口で何を信頼し、何を捨てるか。タイムアウトが防御になる理由

**ステップ**
1. **ヘッダー偽装で IP 制限を突破する**：`X-Forwarded-For` を偽装して `/admin` に入れることを確認する。`real_ip`（`set_real_ip_from`、`real_ip_recursive`）で、信頼できるプロキシからの値だけを使うように直す
2. **レート制限**：`limit_req` で1クライアントあたりの回数を制限する。`burst` と `nodelay` の挙動を確かめる。偽装したヘッダーでレート制限をすり抜けられないことも確認する
3. **slowloris**：わざとゆっくりヘッダーを送るクライアントを自作し、Jetty に直接つないだ場合と nginx を挟んだ場合で、接続がどれだけ埋まるかを比べる。各種タイムアウトで防ぐ
4. **情報を漏らさない**：エラーページやレスポンスヘッダーからバージョンなどが漏れていることを確認し、`server_tokens` やセキュリティヘッダー（HSTS など）で直す
5. **事後チェックとレポート**

**事前チェックの論点**: なぜ `X-Forwarded-For` は右から辿るのか / slowloris が「遅いクライアント」と同じ問題である理由

**事後チェックの例**: `set_real_ip_from` に広すぎる範囲を指定したらどうなるか / レート制限のキーを接続元 IP にすると、大学や会社の NAT の後ろのユーザーはどうなるか

**チェックポイント**
- [ ] 偽装で IP 制限を突破し、`real_ip` で防げた
- [ ] slowloris に対する、直接接続と nginx 経由の差を実測した

## Day 8 — ログインが必要な管理画面を公開したい（深め）

**場面**: 社内向けの管理画面を外から使えるようにしたい。アプリには認証の仕組みがない。入口で認証を入れたが、本当にそれで安全かを確かめたい。

**時代**: ⑤（ゼロトラスト）

**深く理解したいこと**: 入口での認証とアプリでの認可の役割分担。認証結果をアプリに安全に伝える方法

**ステップ**
1. **入口で認証する**：nginx の Basic 認証で管理画面を守る。手軽さと限界を確認する
2. **認証の前段化**：Clojure で小さな認証サービスを作り、`auth_request` で問い合わせる。認証結果をヘッダー（例：`X-Auth-User`）でアプリに渡す
3. **なりすまし**：プロキシを通らずにアプリへ直接届く経路から、ヘッダーを偽装してなりすませることを確認する。経路を塞ぐことと、署名付きトークン（JWT など）をアプリで検証することで防ぐ
4. **IDOR**：ログイン済みのユーザーが、他人の注文番号を指定すると他人の注文が見えることを確認し、アプリ側で認可チェックを入れて直す
5. **事後チェックとレポート**

**事前チェックの論点**: 認証と認可の違い / 入口で判断できる認可とできない認可

**事後チェックの例**: 認証サービスが落ちたら、`auth_request` はどう振る舞うか / トークンの有効期限を長くしたら何が起きるか

**チェックポイント**
- [ ] ヘッダー偽装でのなりすましを再現し、署名検証で防げた
- [ ] IDOR を再現し、アプリ側の認可で直せた

## Day 9 — 業務の Ingress が何をしているか読み解きたい（復習）

**場面**: 業務では ALB → Ingress → Pod で公開しているが、詳しくはわかっていない。Day 1〜8 の知識で読み解く。

**時代**: ④（動的な設定、宣言的な振り分け）

**注意**: 業務のマニフェストや設定は手元で読むだけにして、社外に持ち出さない（このチャットにも貼らず、構造を一般化して話す）

**ステップ**
1. **業務の構成を読む**：Ingress のマニフェストとアノテーション、使っている Ingress コントローラの種類を確認し、Day 1〜8 のどの設定に対応するかを対応表にする
2. **（任意）kind で Ingress を動かす**：ローカルの Kubernetes で Ingress コントローラを動かし、マニフェストから生成された nginx の設定を覗く（Docker の負荷が重ければ省略して、1 を厚くする）
3. **リクエストの旅を図にする**：ALB → Ingress → Pod で、`X-Forwarded-For` が何段になるか、TLS がどこで終端しているか、タイムアウトとリトライがどこで効くかを図にする
4. **網羅の確認と自作の判断**：A〜G のチェックリストで抜けを確認する。Clojure でリバースプロキシを自作する価値があるかを判断する
5. **総合の理解度チェックと全体レポート**

- [ ] 業務の構成を、Day 1〜8 の言葉で説明できる
