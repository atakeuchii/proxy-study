# Day 0 まとめ — リバースプロキシとは何か、なぜ間に挟むのか

## 1. 結論

**リバースプロキシとは、サーバ群の手前に立つ「代理の窓口」。クライアントからの接続をいったん自分が受け取り、中身を見たうえで、裏のサーバへ改めて取り次ぐ。**

- クライアントとサーバは直接つながっていない。「クライアント⇄プロキシ」「プロキシ⇄バックエンド」の**2本の別々の接続**になっている
- クライアントは窓口しか知らない。裏に何台あるか、どう構成されているかを知らない
- フォワードプロキシ（社内プロキシなど）はこの逆で、**クライアント側**の代理として外へ出ていく

### 仕組みは1つ、利点は多数

使い道がたくさんあるのではなく、仕組みは1つ。

> 全リクエストが必ず1か所を通り、そこで中身を見て、手を加え、行き先を選べる

この「関所」としての性質から、次の利点がまとめて出てくる。

| 能力 | 利点の例 |
|---|---|
| 行き先を選べる | パスでの振り分け、負荷分散、落ちたサーバを避ける |
| 中身を見て止められる | レート制限、認証の前段化、サイズ制限 |
| 暗号を剥がせる | TLS終端（アプリは http だけ扱えばよい） |
| 返事を覚えておける | キャッシュ |
| 裏を隠せる | 無停止での入れ替え、内部構成の秘匿 |

### 利点と副作用は同じ根っこから出る

間に1枚挟まるので、副作用もまとめて付いてくる。

- アプリからは、本当のクライアントIPや、元の通信が https だったかが見えなくなる
- プロキシが勝手にリトライすると、二重処理や負荷の増幅が起きる

## 2. 時代ごとの動機

### 時代① Webが重くなる（1990年代半ば〜後半）

- 1台で捌けなくなり、台数を増やす（スケールアウト）と「クライアントはどこにつなぐか」問題が生まれた
- **DNSラウンドロビン**（同じ名前に複数のIPを登録して順番に返す）の問題
  - DNSはサーバの状態を知らないので、落ちたサーバのIPも返す
  - DNSのレコードを直しても、ユーザーのPCや途中のDNSサーバがTTLの間は古い答えを覚えている
  - 大手プロバイダのDNSが1つの答えを覚えると、大勢がそのサーバに集まり負荷が偏る
  - 根本原因：**振り分けを決める場所が自分の手元にない**
- 解決：手前に**ロードバランサ**を置く（Cisco、F5 などのハードウェア製品。初期は L4 が多い）。同時期に、前段の**キャッシュ**（Squid の httpd accelerator モード）も登場
- **本質**：「客が見る住所」と「実際に働く機械」を切り離した。判断のタイミングを「名前を引くとき」から「リクエストが来るとき」へ移した
- 補足：DNS での振り分けは今も、データセンター単位などの大きな振り分けに使われる（DNS で大きく、ロードバランサで細かく、の二段構え）

### 時代② SSLの普及（1990年代後半〜2000年代）

- ハンドシェイクの公開鍵暗号が、当時のCPUには重かった → 専用のカードや前段の装置に任せた（**TLS終端**の始まり）
- 暗号化されると、途中の装置は中身（URL、ヘッダー、Cookie）を読めない → 前段で復号すれば **L7 での振り分け**が可能になる
- 証明書を1か所で管理できる利点もある

### 時代③ C10K問題と遅いクライアント（1999年頃〜2000年代）

- C10K問題：1台で1万の同時接続をどう捌くか（Dan Kegel、1999年）
- Apache（prefork）は1接続を1プロセスが最後まで担当する。プロセスの上限（`MaxClients`）は数百程度
- 遅いクライアントの相手（少しずつ送受信する、keep-alive で接続を開いたままにする）で、プロセスが拘束される
- **足りなかったのはCPUではなく、プロセスの枠（とメモリ）**。CPUは空いているのに新しい客を受け付けられない
- 解決：イベント駆動の **nginx**（2004年公開、Igor Sysoev が Rambler のために開発）を Apache の前に置く
  1. nginx がリクエストを最後まで受け取ってから、Apache に一気に渡す
  2. Apache の返事を nginx が一気に受け取ってバッファに溜める → Apache のプロセスはすぐ解放される
  3. nginx が遅いクライアントに時間をかけて送る
  4. 静的ファイルは nginx が直接返す
- 捌ける数の考え方：

  > 1秒あたりに捌ける数 ＝ 同時に持てる枠の数 ÷ 1リクエストが枠を占有する時間

  nginx を挟んで変わったのは**分母（占有時間）**。CPUを速くしたのでもプロセスを増やしたのでもなく、枠を待ち時間で無駄遣いしなくなった
- **本質（②③共通）**：アプリサーバが本業以外の仕事（暗号の計算、遅い客の相手、静的ファイル）で消耗していた。それを前段に引き取らせ、アプリを本業に専念させた

### 時代④ マイクロサービス（2010年代）

| 困りごと | 解決 |
|---|---|
| 入口が散らかる（クライアントが各サービスの住所を知る必要、認証やレート制限がバラバラ） | **APIゲートウェイ**：入口を1つにまとめ、振り分けと認証をここで行う |
| 住所が絶えず変わる（コンテナはオートスケールやデプロイのたびに IP が変わる） | **動的な設定**：プロキシが外部から一覧を受け取って自動更新。Kubernetes の **Ingress** は、宣言したルールを Ingress コントローラ（中身は nginx など）が読んで自分の設定を書き換える |
| サービス間の通信が壊れやすい（A→B→C と何段も呼ぶ） | タイムアウト、リトライ、サーキットブレーカー、観測。各サービスの横にプロキシを置く**サイドカー**（Envoy、2016年公開）、それを全体に配った**サービスメッシュ**（Istio など） |

- **本質**：プロキシが入口の1台から、サービス間の通信すべてに入り込むインフラになった。設定も手書きから動的・宣言的になった

### 時代⑤ ゼロトラスト（2010年代〜）

- **境界型**（社内ネットワークの内側は安全、外は危険、VPNで内側に入る）が、クラウドやリモートワークで成り立たなくなった。一度侵入されると内側で何でもできてしまう
- Google の **BeyondCorp**（2014年頃から公開）：場所ではなく、リクエストごとに「誰が・どの端末から・何をしようとしているか」を確認する。その確認を行う場所として**アクセスプロキシ**を置く
- 入口での認証（OAuth2 Proxy など）、サービス間の相互認証（mTLS）
- **本質**：プロキシが「このリクエストを通してよいか」を判断する場所になった。「場所で信頼する」から「身元で信頼する」へ

## 3. 副作用と、その対処

### 見えなくなる情報をヘッダーで補う

| ヘッダー | 伝える情報 | なぜ失われるか |
|---|---|---|
| `X-Forwarded-Proto` | 元のスキーム（https / http） | TLS終端で平文になる |
| `X-Forwarded-For` | 本当のクライアントIP | アプリから見た接続元はプロキシの IP |
| `X-Forwarded-Host` | 元のホスト名 | 前段で書き換えることがある |

- 正式な標準として `Forwarded`（RFC 7239）もあるが、現場では `X-Forwarded-*` が主流
- Cloudflare は独自に `CF-Connecting-IP`（本当のユーザーの IP、値は1つ）も付ける

### リダイレクトループ

TLS終端の後ろのアプリが「http なら https へリダイレクト」すると、アプリには常に http に見えるので無限にリダイレクトする（Chrome では `ERR_TOO_MANY_REDIRECTS`）。

対処：nginx で元のスキームを渡し、アプリはそれを見て判断する。

```nginx
proxy_set_header X-Forwarded-Proto $scheme;
```

Clojure では ring-defaults の `:proxy true` がこのヘッダーを読む。

### ヘッダーは誰でも書ける：信頼の境界

- アプリは、届いたヘッダーが「前段が付けたもの」か「クライアントが付けたもの」かを区別できない → **入口で処理する**
- ただし「`X-Forwarded-For` が付いていたら一律にはじく」はダメ。手前に CDN や ALB がいると、正規のリクエストにも最初から付いてくる
- 基準：**直接の接続元（TCP の相手、偽装できない）が信頼できる相手のときだけ、ヘッダーを信じる**

```nginx
set_real_ip_from 10.0.0.0/16;     # このIP範囲(自分たちのALB)から来たときだけ
real_ip_header   X-Forwarded-For; # このヘッダーの値を本当のクライアントIPとして採用する
real_ip_recursive on;             # 信頼できるプロキシを複数経由した場合は、右から辿る
```

- `X-Forwarded-For` はプロキシを通るたびに**右側に追記**される。左端はクライアントが自由に書けるので偽装可能
- 右から順に信頼できるプロキシを飛ばし、最初に出てきた信頼できない IP を本当のクライアント IP とみなす
- よくある事故：アプリが左端の IP をそのまま使い、IP 制限やレート制限を偽装ヘッダーですり抜けられる

### リトライの危険

プロキシは HTTP の形は見えても、**アプリの意味は知らない**。

| 問題 | 内容 |
|---|---|
| 二重処理 | 裏は処理を終えていて返事だけ遅れた場合、POST（注文など）のリトライで二重になる。プロキシには繰り返して安全か（冪等か）がわからない。nginx は既定で POST を別の台へリトライしない |
| リトライストーム | 段ごとのリトライは掛け算で増える（各段3回なら、2段で9回、3段で27回、n段で3ⁿ回）。不調なサーバをリトライがとどめを刺す |

対策：リトライは1か所でだけ行う、リトライの予算（上限）、指数バックオフとジッター、サーキットブレーカー、冪等キー。

→ リトライは「失敗を隠す便利な機能」ではなく、どこで・何を・何回までやるかを設計すべきもの

### 入口とアプリの役割分担

| 置き場所 | 対策 | 理由 |
|---|---|---|
| 入口 | 認証、レート制限、サイズ上限、TLS終端 | 全リクエストが通るので、アプリに届く前にまとめて止められる |
| 入口とアプリの間 | 経路を塞ぐ（内部ネットワーク限定、Kubernetes なら NetworkPolicy） | 入口を迂回されたら入口の対策が無意味になる。IP を書いて判定する方式はコンテナの IP 変化で壊れやすい |
| アプリ | 署名付きトークンの検証、認可 | 注文データの中身を知っているのはアプリだけ。入口の判断を鵜呑みにしない |

- **認証**（誰か）は入口でできる。**認可**も「`/admin` は管理者のみ」のような粗い単位なら入口でできるが、「この注文を見てよいか」はデータを持つアプリにしかできない
- 他人の ID を指定すると他人のデータが見える脆弱性：**IDOR / BOLA**（OWASP API Security Top 10 の1位）
- 認証結果をただのヘッダー（`X-Auth-User: yamada`）で渡すと、入口を迂回した経路から偽装できる → 入口が秘密鍵で署名したトークン（JWT など）を渡し、アプリが署名を検証する。鍵を持たない人には正しい署名が作れない
- 経路を塞ぐことと署名の検証は**両方行う**（多層防御）

> プロキシは関所であって、城の中の各部屋の鍵ではない

## 4. 小さなシステムでも置く理由

裏のサーバが1台でも、リバースプロキシを置く価値はある。

- **切り離し**：裏のアプリを入れ替えたり増やしたりしても、クライアントにとっての入口は変わらない
- **TLS終端**：アプリは http のまま、証明書の管理を入口に集約できる
- **入口で守る**：レート制限、サイズ上限、アプリのポートを外に晒さない
- **観測**：アクセスログを1か所で取れる
- **入口の統一**：アプリが2つ以上になったら、1つのドメイン・443番ポートの下にまとめられる

## 5. 自分の構成の棚卸し

AWS と Kubernetes の典型的な構成では、1つのリクエストが複数のプロキシを通る。

```
ブラウザ
  │ ① DNS（Route 53）           … 大きな単位の振り分け
  ▼
② CDN（CloudFront）            … キャッシュ、TLS終端、DDoS吸収
  ▼
③ ALB / NLB                     … 負荷分散、TLS終端（ALB は L7、NLB は L4）
  ▼
④ Ingress コントローラ          … パスやホスト名での振り分け（中身は nginx など）
  ▼
⑤ Service（kube-proxy）         … Pod への振り分け（L4）
  ▼
⑥ （あれば）サイドカー         … サービスメッシュ
  ▼
Pod（アプリ）
```

| 環境 | 構成 | プロキシが担っていること・関係する話 |
|---|---|---|
| 業務 | ALB（③）→ Kubernetes Ingress（④）→ Pod | 典型構成そのもの。詳細は Day 9 で読み解く |
| 自宅サーバ | Cloudflare（`cloudflared` による Tunnel）で公開。nginx は使っていないはず | Cloudflare 自体が巨大なリバースプロキシ（TLS終端、キャッシュ、DDoS吸収）。アプリから見た接続元は `cloudflared`。本当の IP は `CF-Connecting-IP` で知る |
| いしなび | フロントは GitHub、API は Cloud Run（＋無料 DB） | Cloud Run の手前の Google のフロントエンドが、TLS終端と台数の増減を担う。フロントと API が別ドメインなので CORS が必要（Day 1 の題材） |

### 自宅サーバ（Cloudflare）で本当の IP を扱うときの注意

- Cloudflare 側の設定は不要。Cloudflare が最初から `CF-Connecting-IP` と `X-Forwarded-For` を付けてくる。**こちら側（nginx やアプリ）が読む設定をする**
- 信頼できる相手（Cloudflare の IP 範囲、Tunnel なら `cloudflared`）から来たときだけヘッダーを信じる
- Cloudflare を迂回してアプリに直接届く経路を塞ぐ。Tunnel は自宅側のポートを開けずに済むので有利
