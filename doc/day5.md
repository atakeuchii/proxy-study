# Day 5 レポート — リアルタイム通知を通したい（長い接続と大きなデータ）

## 1. 目的

### 1.1 背景（どの時代の困りごとか）

- **時代③（C10K と接続の扱い）**：nginx は、たくさんの接続を少ない資源で受け持ち、返事を溜めてアプリを守るために作られた。その既定の振る舞いは「すぐ終わる普通のリクエスト」を前提にしている
- SSE や WebSocket のような**長くつながり続ける接続**、大きなアップロードは、その前提から外れるため、既定のままでは不具合が出る

### 1.2 確かめたいこと

1. nginx のバッファリングは、SSE にどう影響するか
2. 長い接続は、なぜ・どのように切られるか
3. WebSocket への切り替えは、なぜ nginx を通るとつながらないか
4. 大きなアップロードと、裏への接続の使い回しは、既定ではどうなっているか

---

## 2. 手法

### 2.1 構成（`compose.day5.yml`）

```
client ──→ proxy(nginx: 8301〜8303) ──→ api-a
  └──────────── 直接 ──────────────────→ api-a:3000(比べるため)
```

### 2.2 nginx の入口（`nginx/day5.conf`）

| ポート | 中身 |
|---|---|
| 8301 | 既定のまま |
| 8302 | 対応済み：`/events` は `proxy_buffering off`・`proxy_read_timeout 1h`、`/ws` は `proxy_read_timeout 1h`、`/upload` は `client_max_body_size 100m`。全体で `proxy_http_version 1.1`、`Upgrade` / `Connection` ヘッダーの引き継ぎ、upstream の `keepalive 16` |
| 8303 | 8302 と同じで、`proxy_read_timeout 5s`（切れる様子を短時間で見るため） |

### 2.3 アプリ（`server.clj` に追加）

| エンドポイント | 中身 |
|---|---|
| `GET /events?n=&interval-ms=&heartbeat-ms=&accel=` | SSE。1件ごとに flush する。`heartbeat-ms` があれば、イベントの間に `: ping` を書く |
| `GET /ws` | WebSocket のエコー。切り替えの依頼がなければ 426 |
| `POST /upload` | 本文を読み切って、バイト数を返す |
| `/stats` の `connections-total` | アプリが受け付けた TCP 接続の数 |

### 2.4 仕組みの分担

| やっていること | 担当 |
|---|---|
| SSE のイベントを1件ずつ書いて flush する | アプリ |
| 受け取った SSE を溜めずに流す | nginx（`proxy_buffering off`）。アプリが `X-Accel-Buffering: no` で頼むこともできる |
| 長い接続を切らない | nginx（`proxy_read_timeout`） |
| 何もないときも定期的にデータを送る | アプリ（ハートビート） |
| WebSocket への切り替えの依頼を引き継ぐ | nginx（`proxy_http_version 1.1`、`Upgrade` / `Connection`） |
| 大きな本文を受け付ける | nginx（`client_max_body_size`） |
| 裏への接続を使い回す | nginx（upstream の `keepalive`） |

## 3. 結果

### 3.1 Step 1：SSE（1秒ごとに5件）

| 経路 | nginx | 届き方 |
|---|---|---|
| 直接 | — | 1秒ごとに1件 |
| 8301（既定） | 1.30.6 | 1秒ごとに1件 |
| 8302（対応済み） | 1.30.6 | 1秒ごとに1件 |
| 8301（既定） | **1.24** | 14:10:53〜57 に書かれた5件が、すべて 14:10:57 にまとめて届いた |
| 8302（対応済み） | 1.24 | 1秒ごとに1件 |

1.30.6 と 1.24 で、同じ設定のまま振る舞いが違った。

### 3.2 Step 2：長い接続が切れる（8303、タイムアウト5秒）

| 測定 | 結果 |
|---|---|
| イベントの間隔 8秒、ハートビートなし | 1件目（14:14:28）の後に切れた。curl の終了コード 18 |
| イベントの間隔 8秒、ハートビート 2秒 | 2秒ごとに `: ping` が届き、3件すべて届いた。終了コード 0 |

### 3.3 Step 3：WebSocket

| 測定 | 結果 |
|---|---|
| 8301 に切り替えを依頼 | 426。アプリが返したもので、アプリに届いた `upgrade` は `null` |
| 8302 に切り替えを依頼 | 101 Switching Protocols |
| 8303 で切り替えた後、何も送らずに待つ | 101 の後、5.03秒で接続が切れた |

### 3.4 Step 4：アップロードと接続の使い回し

| 測定 | 8301 | 8302 |
|---|---|---|
| 5MB のアップロード | 413（nginx が返した HTML） | 200、`received-bytes: 5000000` |
| 100回のリクエストで、アプリが受け付けた新しい接続 | 100 | 1 |

## 4. 考察

### 4.1 SSE は「終わらない返事」なので、溜めてから送る仕組みと相性が悪い

nginx 1.24 の既定（バッファリングあり）では、1秒ごとに書かれたイベントが、まとめて遅れて届いた。nginx は受け取った返事を溜め、バッファがいっぱいになるか返事が終わったときに送る。普通の返事なら「終わり」がすぐ来るが、SSE の返事は終わらないので、イベントが溜まり続ける。Day 2 で遅いクライアントからアプリを守ったバッファリングが、ここでは「リアルタイム」を壊す。

一方、nginx 1.30.6 では、既定の設定のままでもイベントがすぐ届いた。HTTP のバージョンの既定値の違い（後述）も疑ったが、1.24 で裏とのやりとりを HTTP/1.1 にしてもまとめて届いたので、それが原因ではない。何が変わったのかは確かめられていない。

いずれにせよ、同じ設定でもプロキシのバージョンで振る舞いが変わる。SSE の場所では `proxy_buffering off` や `X-Accel-Buffering: no` で**明示的に**バッファリングを切っておけば、手前にどんなプロキシがいても同じように動く。

アプリの中にも同じ問題がある。Jetty の出力バッファ（32KB）に溜まらないよう、`sse-body` はイベントやハートビートを書くたびに flush している。

### 4.2 長い接続は「何も流れない時間」で切られる

`proxy_read_timeout` は、返事の全体ではなく「前にデータを受け取ってから次を受け取るまでの間隔」の上限である。アプリが正常でも、イベントの間隔がタイムアウトより長いと、nginx は裏が止まったと判断して切る（終了コード 18）。2秒ごとのハートビートを送ると、何も流れない時間が最長2秒になり、切られなくなった。WebSocket でも同じで、101 で切り替わった後、5秒間何も流れなかったので切られた。既定の60秒なら「1分で切れる」になる。

経路上のすべてのプロキシ（CDN、ALB、会社のプロキシなど）の設定を自分で変えられるとは限らないので、プロキシ側でタイムアウトを延ばすだけでなく、アプリ側でハートビート（SSE なら `: ping`、WebSocket なら ping / pong）を送るのが一般的である。

### 4.3 WebSocket の切り替えには、nginx が転送しないヘッダーを引き継がせる必要がある

8301 では、curl が送った `Upgrade: websocket` がアプリに届かなかった（`upgrade: null`）。`Connection` と `Upgrade` は「隣の相手との1区間だけ」のホップバイホップヘッダーなので、nginx は既定で次へ転送しない。8302 では、`proxy_http_version 1.1` と、`Upgrade` / `Connection` を引き継ぐ設定で、101 が返った。Day 1 の「プロキシを挟むと見えなくなる情報をヘッダーで補う」と同じ構図で、今回は nginx がわざと転送しないものを、設定で引き継がせている。

### 4.4 大きなアップロードと、接続の使い回し

5MB のアップロードは、8301 では nginx がアプリに届ける前に 413 で断った（既定の上限は 1MB）。上限は、巨大なリクエストでメモリやディスクを使い切られないためのもので、アップロードを受ける場所だけ必要な大きさに上げる。

nginx は既定でアップロードを全部受け取ってから送る（`proxy_request_buffering on`）。回線の遅いユーザーの相手は nginx が引き受け、アプリのスレッドが拘束されるのは受け取り終えた後の一瞬だけになる。Day 2 の返事の向きのバッファリングと同じことを、リクエストの向きでもしている。

8301 では100回のリクエストで接続を100回張り直し、8302 では1本を使い回した。使い回しには、upstream の `keepalive` に加えて、`proxy_http_version 1.1` と、普通のリクエストで `Connection` を空にする設定（`map` で WebSocket 以外は `''`）が必要だった。nginx は既定で裏へ `Connection: close` を付けるためである。WebSocket の対応と接続の使い回しは、同じ2行で成り立っている。

### 4.5 HTTP のバージョンについて分かったこと

nginx のドキュメントでは、`proxy_http_version` の既定は **1.29.7 から 1.1**（それより前は 1.0）で、1.29.4 から `2` も指定できる。`3` は指定できない。裏を HTTP/2 にするにはアプリ側も HTTP/2 で受けられる必要があり、近くにいるアプリと keepalive で接続を使い回すなら HTTP/1.1 で十分なことが多い。プロキシの前後は別々の接続なので、外側は HTTP/2 や 3、裏は HTTP/1.1 のように、違うバージョンで話せる（プロトコル変換）。

### 4.6 事後チェックで分かったこと：nginx では救えないもの

- **SSE の接続はスレッドを占有し続ける**：今日の `/events` は待っている間もスレッドを手放さない。枠16本なら、SSE のユーザーが16人そろった時点で枠が埋まり、以降は SSE も普通のリクエストも、画面が閉じられるまで待たされる。nginx のバッファリングは「出来上がった返事」を預かる仕組みなので、「これから作られる返事」を待つ時間は肩代わりできない。待っている間はスレッドを返す非同期の作りにするか、SSE を別のサービスに分ける必要がある
- **`proxy_http_version 1.1` を消すと**（1.29.7 より前）：WebSocket は 426、接続は毎回張り直し（100本）になる。1.29.7 以降は既定が 1.1 なので変わらない
- **`proxy_request_buffering off` にすると**：遅いアップロードがそのままアプリに流れ、本文を読み終えるまでスレッドが拘束される。20人が1分かけて送ると、16本の枠がすべて埋まり、普通のリクエストも待たされる。nginx は少数のプロセスで多数の接続を受け持てるので、溜めておけばこの問題は起きない

### 4.7 その他：nginx の設定は起動時に一度だけ読まれる

途中で `day5.conf` の説明のコメントから `#` だけを外したため、設定が壊れていたが、nginx 1.30.6 は動き続けていた。`docker compose up -d --build` は、設定（イメージなど）が変わっていないコンテナを作り直さないので、nginx は編集前の設定のまま動いていた。イメージを変えて作り直したときに初めて新しい設定を読み、エラーになった。設定を変えたら、`nginx -t` で確かめてから reload する。

---

## 5. 結論

1. SSE は終わらない返事なので、溜めてから送るバッファリングと相性が悪い。nginx 1.24 では既定のままだとイベントがまとめて遅れて届き、1.30.6 では届いた。バージョンに左右されないよう、SSE の場所ではバッファリングを明示的に切る
2. 長い接続は、何も流れない時間がタイムアウトを超えると切られる。プロキシのタイムアウトを延ばし、アプリからハートビートを送る
3. WebSocket の切り替えに必要な `Upgrade` / `Connection` は、nginx が既定で転送しない。HTTP/1.1 にしてヘッダーを引き継がせる。同じ設定が、裏への接続の使い回しにも必要である
4. nginx は大きなアップロードを既定で 1MB に制限し、受け取ってから送ることでアプリを遅いユーザーから守る。一方、SSE のように「アプリ自身がつながり続ける」接続は、nginx では救えず、アプリの作り（非同期化、サービスの分離）で解決する必要がある

### 残った課題

- nginx 1.30.6 で、既定の設定でも SSE がすぐ届いた理由は未確認
