# Day 1

| 用語 | 意味 |
|---|---|
| **オリジン** | 「スキーム＋ホスト名＋ポート」の組。`http://localhost:8000` と `http://localhost:3001` は、ポートが違うので別オリジン |
| **同一オリジンポリシー** | ブラウザの安全のための決まり。あるオリジンのページの JS は、別オリジンへのリクエストの**返事を原則読めない** |
| **CORS** | Cross-Origin Resource Sharing。別オリジンの返事を読んでよいかを、サーバが `Access-Control-Allow-Origin` などのヘッダーで許可する仕組み |
| **プリフライト** | CORS で、本番のリクエストの前にブラウザが自動で送る確認用の `OPTIONS` リクエスト。JSON を送る POST などで発生する |
| **upstream** | nginx から見た「裏のサーバ」。nginx の設定では `upstream` ブロックでまとめて定義できる |
| **`server` ブロック** | nginx の設定で、「どのポート・どのホスト名のリクエストを受けるか」の単位 |
| **`location` ブロック** | `server` ブロックの中で、「どのパスのリクエストをどう処理するか」を書く単位 |
| **`proxy_pass`** | `location` の中で、リクエストを裏のサーバへ転送する指示 |
| **名前ベースのバーチャルホスト** | 1つの IP とポートで、`Host` ヘッダーのホスト名を見て別々のサイトを返す方式 |
| **`Host` ヘッダー** | ブラウザが「どのホスト名宛てか」を伝える HTTP ヘッダー。プロキシを通ると書き換わることがある |
| **SNI** | TLS のハンドシェイクの最初に、クライアントが接続先のホスト名を平文で伝える仕組み。暗号化前にどの証明書を使うか決めるために必要 |
| **mkcert** | 自分の PC 専用の認証局を作り、ブラウザに信頼される証明書をローカルで発行するツール |
| **L4 / L7** | L4 は IP とポートだけを見て転送する。L7 は HTTP の中身（パス、ヘッダー）まで見て転送する |
| **`stream` モジュール** | nginx で L4（TCP/UDP）の転送を行う機能。普段の `http` の設定とは別のブロックに書く |
| **Compose のネットワーク** | Docker Compose が自動で作る内部ネットワーク。コンテナ同士はサービス名（`api-a` など）で通信できる |

# Day 2

## 性能を測るときの言葉

| 用語 | 意味 |
|---|---|
| **スループット** | 1秒あたりに処理し終えたリクエストの数（req/s）。「どれだけ捌けるか」 |
| **レイテンシ（応答時間）** | 1つのリクエストを送ってから、返事を受け取り終えるまでの時間。「1人がどれだけ待つか」 |
| **p50 / p99** | レイテンシを短い順に並べたとき、50% / 99% の位置の値。p99 は「100人に1人が経験する遅さ」。平均だと一部の極端に遅いリクエストが見えにくいので、こちらを使う |
| **同時実行数（並行数）** | 負荷ツールが同時に送り続けるリクエストの数。`oha -c 10` なら、常に10本のリクエストが飛んでいる状態を保つ |
| **リトルの法則** | 「系の中にいる数 ＝ 到着率 × 1件あたりの滞在時間」（L = λW）。Day 0 の「捌ける数 ＝ 枠の数 ÷ 占有時間」は、これを枠に当てはめたもの |
| **oha** | HTTP の負荷ツール。指定した同時実行数でリクエストを送り続け、スループットやレイテンシの分布を表示する |

## 枠とバッファ

| 用語 | 意味 |
|---|---|
| **スレッドプール** | あらかじめ用意したスレッドの集まり。Jetty は、1つのリクエストの処理（読む・計算する・書く）を、プールのスレッド1本が最後まで担当する |
| **`max-threads`** | Jetty のスレッドプールの上限。ここが Day 0 の Apache の `MaxClients` にあたる「枠の数」 |
| **キュー（待ち行列）** | 空いているスレッドがないとき、リクエストが並んで待つ場所。並んでいる間もレイテンシは伸び続ける |
| **ソケットの送信バッファ** | OS（カーネル）が接続ごとに持つ、送信待ちのデータの置き場所。アプリが書いたデータは、まずここに入る。相手の受信が遅くてここが一杯になると、アプリの書き込みが止まる（ブロックする） |
| **遅いクライアント** | 回線が遅い、またはわざとゆっくり受け取るクライアント。`curl --limit-rate 50k` で、受信速度を毎秒 50KB に制限して再現できる |
| **`proxy_buffering`** | nginx の設定。`on`（既定）なら、裏の返事をいったん nginx が全部受け取ってから、クライアントへ送る。`off` なら、受け取った分をその場で流す |
| **`proxy_buffers` / `proxy_buffer_size`** | 返事を溜めておく、メモリ上のバッファの数と大きさ |
| **`proxy_max_temp_file_size`** | メモリのバッファに入りきらない返事を、一時ファイル（ディスク）に溜めるときの上限 |
| **`proxy_request_buffering`** | リクエスト側のバッファリング。`on`（既定）なら、クライアントから本文（アップロードなど）を全部受け取ってから、裏へ送る |

## 負荷分散

| 用語 | 意味 |
|---|---|
| **ラウンドロビン** | 裏のサーバに順番に配る方式。nginx の既定 |
| **`least_conn`** | その時点で処理中の接続が一番少ないサーバに配る方式 |
| **`ip_hash`** | クライアントの IP アドレスから計算した値で、配る先を決める方式。同じ IP からは、いつも同じサーバに届く |
| **`weight`** | upstream の各サーバに付ける重み。`weight=2` なら、他の2倍の割合で配られる |
| **偏り** | 配る回数は均等でも、重いリクエストが特定のサーバに集まるなどして、サーバごとの負荷が不均等になること |

## セッション

| 用語 | 意味 |
|---|---|
| **セッション** | 「同じ人からの一連のアクセス」をサーバ側で覚えておく仕組み。サーバは Cookie にセッション ID を入れて渡し、次のリクエストでその ID を受け取って、覚えておいたデータを引き出す |
| **インメモリセッション** | セッションのデータを、アプリのメモリの中に置く方式。手軽だが、そのアプリのプロセス（そのサーバ）の中にしかない |
| **スティッキーセッション** | 同じクライアントを、いつも同じサーバに送り続ける負荷分散の方式。`ip_hash` や Cookie を使って実現する |
| **セッションの外出し** | セッションのデータを、全サーバから共通に見える外部の保存先（Redis など）に置く方式。どのサーバに届いても同じデータを引ける |
| **NAT** | 複数の端末が、1つのグローバル IP アドレスを共有して外に出る仕組み。家庭のルーター、会社や大学のネットワーク、携帯回線などで使われる。外から見ると、大勢が同じ IP に見える |
